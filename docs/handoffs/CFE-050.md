# CFE-050 — End the session when its refresh is rejected

When `/auth/refresh` returns 401 mid-session, end the session through one
shared `endSession`, with one toast and the existing `RequireAuth` redirect,
rather than staying logged in with every request failing. Grilled
2026-10-02, from tech-debt pass #4 finding 1
(`docs/findings/2026-10-02-tech-debt.md`).

**Implementation mode**: AI-driven.

## Facts this rests on (checked 2026-10-02)

- Access token 15 min, refresh token 7 days, rotated on each use
  (`crockpot-go/internal/auth/jwt.go:26-27`, `internal/handler/auth_handler.go:20`).
  Mid-session death means a revocation (logout elsewhere, reuse detection,
  password reset) or a tab idle for 7+ days.
- `POST /auth/refresh` returns 401 for every "session is gone" case
  (`invalid_refresh_token` for missing/invalid/revoked/reused, `unauthorized`
  for a deleted user), 500 for internal errors, 429 from its rate limiter
  (`auth_handler.go:717-791`, `main.go:140-143`).
- Public routes never return 401 for a bad token (`OptionalAuthMiddleware`,
  `internal/middleware/optional_auth.go:19-22`), so only protected requests
  trigger a refresh.
- `POST /auth/logout` has no auth middleware (`main.go:128-137`), so
  logging out never triggers a refresh.
- The access token isn't checked against revocation: another tab keeps
  working for up to 15 min after a logout elsewhere.
- Concurrent 401s already share one refresh (`refreshPromise`,
  `client.ts:43-50`; tested at `client.test.ts:116`).
- Every API error toast comes from one of three wrappers: `useApiQuery:26`,
  `useApiInfiniteQuery:48`, `useApiMutation:20`.
- User-scoped queries (menu, shopping list, favourites, My recipes) are
  `enabled: isAuthenticated`.
- `packing-list-react` has the same gap (`src/lib/api/client.ts:17-29`), so
  there is no precedent to copy.

## Decisions

1. **Only a 401 from `/auth/refresh` ends the session.** A 429, 5xx or
   network failure is transient: the session and the access token are kept,
   and the request fails with a normal error. This matches the boot rule in
   `fetchSession` (`CFE-002a`). `performRefresh` stops clearing the token on
   non-401 failures. Why: a blip shouldn't log someone out mid-recipe; a
   missed real expiry costs one more toast before the next 401.
2. **The transport calls a handler the app registered; it doesn't reach
   into the app.** `client.ts` exports `onSessionExpired(listener)` (it
   returns an unsubscribe function) and calls listeners from the 401 branch
   of `performRefresh`, before the refresh promise rejects. Because of the
   singleton `refreshPromise`, it fires once per failed refresh, however many
   requests were waiting. `AuthProvider` subscribes in an effect.
   - Rejected: `client.ts` importing `queryClient` and clearing caches itself
     (the transport would learn the auth feature's cache layout); a `window`
     event (no type checking); global `QueryCache`/`MutationCache` `onError`
     (fires once per failed query, and `lib/` would import the auth feature).
   - Rejected: moving the session out of TanStack Query into an external
     store. Judged on its merits: the user is server state, which is what
     the query cache is for, and the query already handles boot retry and
     StrictMode de-duplication. An external store would still need a bridge
     to wipe caches. `CFE-022` was a misuse of `clear()`, not a flaw in the
     model.
3. **One `endSession(queryClient)`, the only code that ends a session.** It
   clears the access token, writes the session query to `null`, then
   removes every other query (the `CFE-022` order, moved out of
   `useLogout`). It returns `true` only if a signed-in user was there to
   end; with the session already `null`, or not yet loaded, it does
   nothing else and returns `false`. Each caller picks its own toast:
   `AuthProvider` shows `toast.info("Your session has ended. Please sign
   in again.", { id: "session-expired" })` when it returns `true`, and
   `useLogout` keeps its existing success-only "Logged out". *Changed
   while building:* the grill had `endSession` take a `reason` and toast
   itself, but `useLogout` calls it from `onSettled`, which would have
   shown "Logged out" after a failed logout too (`useLogout.test.tsx`
   locks that out). `AUTH_SESSION_QUERY_KEY` moved to
   `auth/data/queryKeys.ts` to avoid an `AuthContext` ↔ `endSession`
   import cycle. Future callers: account deletion (`CROC-030`), forced
   logout after a password reset.
4. **Only a signed-in session is ended** (the `endSession` guard). At boot, an anonymous visitor's refresh gets a 401 too, while
   the session query has no data. That is ignored, so no toast for someone
   who was never signed in, including a visitor returning after 7+ days
   (they just land logged out, which is right for a fresh load).
5. **Requests that fail because the session ended throw
   `SessionExpiredError`** (a subclass of `ApiError`, status 401), so
   `instanceof ApiError` and status checks keep working. A new
   `toastApiError(error)` replaces the copied toast line in the three
   wrappers and skips `SessionExpiredError`. Errors still propagate:
   mutations' `onError` and rollbacks run, and queries end in their error
   state. Why: the expiry toast already explains it, and N per-request
   toasts saying "failed to refresh session" are noise.
6. **Where the user lands: no change.** On a protected route, `RequireAuth`
   redirects to `/`. On a public route the user stays, the header switches
   to Sign in, and user-scoped queries switch off.
7. **An unsaved recipe form is lost.** `RequireAuth` unmounts it in the same
   render, so the leave prompt never fires. Accepted for now; `CFE-048`
   (drafts) is the real fix and records this case. The toast copy
   deliberately doesn't promise "pick up where you left off".
8. **A refresh that succeeds but whose retried request still gets 401** is
   an ordinary `ApiError`, not an expiry.

## Acceptance criteria

- [ ] A protected request → 401, refresh → 401: the listener fires once,
      the request rejects with `SessionExpiredError`, and the access token
      is `null`.
- [ ] Three concurrent protected requests hitting that path: one refresh
      call, the listener fires once, all three reject with
      `SessionExpiredError`.
- [ ] Refresh → 429, 500, or network `TypeError`: the listener does not
      fire, the access token is unchanged, and the request rejects with a
      normal `ApiError`/`TypeError`.
- [ ] Refresh succeeds, retry → 401: plain `ApiError(401)`, no listener call.
- [ ] `endSession(qc)` with a user present: session query is `null`, all
      other queries are removed, the token is cleared, and it returns `true`.
- [ ] `endSession` with the session already `null` does nothing (no toast,
      no wipe).
- [ ] `useLogout` goes through `endSession(qc)`, and its existing tests
      still pass.
- [ ] `AuthProvider`: a session-expired event during boot (no user yet)
      does nothing; with a user present, it ends the session.
- [ ] The three wrappers toast through `toastApiError`; `SessionExpiredError`
      produces no toast; other errors toast as before.
- [ ] No optimistic rollback recreates a cache that `endSession` removed
      while its request was in flight: all four menu transforms, and the
      three shopping-list hooks. *Found while building:* the grill claimed
      the rollbacks were already safe, but `clearEntries.revert` and the
      three shopping-list hooks' whole-snapshot restores recreated the
      wiped cache. Once `CFE-002b` adds in-page login, that would show the
      previous user's menu or list to the next user for up to 5 min. Fixed
      with a "do nothing if the cache has gone" guard
      (`shopping-list/utils/restoreShoppingList.ts`).
- [ ] Integration: a routed protected page whose query hits 401 + refresh
      401 ends up on `/`, with exactly one toast on screen.
- [ ] Lint shows no new warnings; the full suite passes.

## Non-goals

- Ending the session in other open tabs straight away (`BroadcastChannel`).
  Other tabs end on their next refresh, within 15 min. A small follow-up
  later if wanted: it would broadcast from `endSession`.
- Returning the user to the page they were on after signing back in
  (`AuthCallback` always goes to `/menu`; a return path through the Google
  redirect has open-redirect concerns).
- Keeping or restoring an unsaved recipe form (`CFE-048`).
- A "Sign in" action button on the toast.
- Any `crockpot-go` change.

## Verification

- **Logic with assertable behaviour (failing test first)**:
  `src/lib/http/client.test.ts` (criteria 1–4), new `endSession` tests,
  `AuthContext.test.tsx`, `useLogout.test.tsx`, `toastApiError` tests, the
  rollback case in `useOptimisticMenuMutation.test.tsx`, and one routed
  integration test. Run with `npx vitest run`.
- **API boundary and hands-on (founder)**, against local `crockpot-go`:
  1. Log in and open Menu.
  2. Change both `JWT_SECRET_ACCESS` and `JWT_SECRET_REFRESH` in
     `crockpot-go`'s `.env` and restart it. Click something on Menu. The
     next request gets 401 and the refresh gets 401. Expect: one "Your
     session has ended" toast, redirect to `/`, header shows Sign in, no
     other toasts.
  3. Repeat on a recipe detail page: you should stay on the page, see the
     header switch, and the baskets disappear.
  4. Log in again, set DevTools to Offline, and click something. Expect a
     normal error toast; still logged in after going back online.
  5. Log out normally: one "Logged out" toast, as before.
