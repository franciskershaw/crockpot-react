# CFE-031 — Feature-folder reorg (recipes split + data/ bucket)

Grilled 2026-09-18.

**Implementation mode: started hand-written, switched to AI-driven
partway through** once the founder hit real friction on the volume of
import edits — confirmed explicitly, not assumed. Claude picked up from
the partial manual state (the `recipes/data/` move) and completed the
rest, including a follow-on round of smaller structural fixes raised
after a full-tree walkthrough post-move (decisions 9–13 below).

## Summary

`features/recipes/` has outgrown being one feature: 30 `components/`
files and 11 `hooks/` files serving two different routed pages
(`/recipes` browse, `/recipes/:id` detail) plus a handful of genuinely
shared pieces, all flattened together. Import-graph tracing (not
guesswork — every consumer was grepped) showed the split is mechanical:
split `recipes/` into a shared core plus two page-specific sibling
features. Alongside that, every feature's loose `api.ts`/`types.ts`/
`queryKeys.ts` move into a new `data/` bucket — a founder preference
("I'm not a fan of loose files in the root of a feature"), applied
project-wide in this same ticket since it's a small, mechanical retrofit
and leaving `auth/`/`menu/` inconsistent with a brand-new rule would
undercut the point of having it.

## Decisions and why

### 1. Split `recipes/` into `recipes/` (shared) + `recipes-browse/` + `recipes-detail/`

Traced every import in `src/features/recipes/{components,hooks}` against
which page consumes it exclusively vs. which is used by 2+ page-features
today, or is a confirmed future consumer (decision 7 below covers the
one exception to "today's import graph"). Result below in "Target
structure." Rejected: keeping one flat
`recipes/` folder (the status quo — the entire reason this ticket
exists) and the earlier `filters/`+`browse/` by-concern split rejected at
`CFE-004`'s grill (2026-09-05) for being a judgment call with no
mechanical line. This split's line is grep-able: "how many routed pages
import this file."

### 2. Naming: `recipes-browse/` + `recipes-detail/`, both plural

Matches the shared `recipes/` folder's pluralization. Concrete reason
beyond consistency: in an alphabetical directory listing, `recipes-browse/`
and `recipes-detail/` sort immediately after `recipes/` (each has
`recipes` as a literal prefix), so the three cluster together when
scanning `features/`. A singular `recipe-detail/` would instead sort
*before* `recipes/` (`-` < `s`), breaking that grouping. Rejected: the
ticket's own original draft (`recipes-browse/` + `recipe-detail/`,
inconsistent) and shorter alternatives (`browse/`, `detail/` alone —
too generic once the codebase has other browse/detail-shaped screens,
e.g. a future favourites list).

### 3. `useRecipePermissions`/`useDeleteRecipe` move to shared `recipes/` pre-emptively; their button components (`RecipeEditButton`/`RecipeDeleteButton`) do not

Both hooks are `recipes-detail/`-only by today's import graph, but
`CFE-008` ("My recipes tab: create/edit/delete own recipes") is already
backlogged and will need the same permission check and delete mutation.
Moving the *logic* now avoids moving it twice. The *button components*
that currently call these hooks stay in `recipes-detail/`: a button's
presentation is a real bet on what `CFE-008`'s UI will look like (a
hero icon-button vs. a list-row action could differ completely), and
generalizing a component before a second real caller exists is the
premature-abstraction trap this project already got burned by once
(`LESSONS.md` 2026-09-08 — the `AddToMenuButton` split that grew the
file instead of shrinking it). `CFE-008`'s own grill decides fresh
whether to reuse or duplicate the button; the hook is shared either way,
so nothing is blocked.

### 4. `ingredientCategories.ts` moves to `recipes-detail/` (loose, not in `data/`)

Its only consumer, `IngredientsSection.tsx`, is `recipes-detail/`-only.
It's a plain icon/grouping helper, not an api/types/queryKeys file, so
it doesn't belong in the new `data/` bucket either — it stays a loose
"single-purpose file with no natural bucket" at `recipes-detail/`'s
root, per the feature-folder rule's existing exception.

### 5. New `data/` bucket for `api.ts`/`types.ts`/`queryKeys.ts`, retrofitted to every feature that has them

Founder preference, not a technical requirement: loose singleton files
at feature root read as messy. Scope is strict — only these three file
kinds. Checked before deciding: `types.ts`'s `RecipeDetail extends
RecipeCard` (so `types.ts` can't split by page without one side
importing from the other anyway) and `queryKeys.ts`'s `recipeKeys`
object nests both `lists()` and `details()` under one shared `all` root
key, used for invalidating both together after a favourite/delete
mutation — real coupling, not incidental, so these three files stay
**unified** in shared `recipes/data/`, not split by page like
`components/`/`hooks/` are. Two files that don't fit the strict
api/types/queryKeys definition — `auth/googleLogin.ts` (a one-line OAuth
redirect trigger) and `ingredientCategories.ts` (decision 4) — stay
loose at their feature root rather than becoming a catch-all. Rejected:
a broader "anything not pages/components/hooks goes in data/" rule,
which would mix genuinely different kinds of files and recreate the
vague-bucket problem the pages/components/hooks split exists to avoid.

### 6. `MenuScreen.tsx` → `menu/pages/MenuPage.tsx` (renamed, not just moved)

Every other routed page is `*Page.tsx` (`LandingPage`, `BrowseRecipesPage`,
`RecipeDetailPage`); `MenuScreen` predates that convention (`CFE-001`/
`CFE-002a`). Cheap to fix while the file and its one import site are
already being touched.

### 7. `RecipeCard`/`RecipeCardSkeleton` stay shared despite being browse-only by today's import graph — correcting an error from the grill

Re-checked with a stricter grep (word-boundary, not substring) after the
grill: `<RecipeCard>` is only ever rendered by `RecipeGrid.tsx`, and
`RecipeCardSkeleton` only by the same file — both **browse-only** today.
The grill's original claim that `landing/` renders `RecipeCard` was a
grep false-positive (it matched `RecipeCardPlaceholder`, an unrelated
component landing already has its own copy of) and should be
disregarded. The actual reason these two stay in shared `recipes/` is
the same class of pre-emptive move as decision 3: `CFE-006` (Menu tab),
`CFE-007` (Favourites tab), and `CFE-008` (My recipes tab) are all
backlogged and will all need some recipe-card-shaped display — a
stronger signal than decision 3's single-ticket case, since three
separate tickets converge on the same need. Caveat: `RecipeCard`'s
*internal shape* will likely still need to change once Epic 3 lands
(e.g. its hardcoded add-to-menu action becoming a slot, since the Menu
tab wants "remove from menu," not "add to menu") — that's a future
ticket's refactor, not blocked by or decided by where the file lives now.

### 8. `add-to-menu/` subfolder is dissolved; `AddToMenuCTA` moves alone to `recipes-detail/`

Current import graph (re-checked, word-boundary greps): `AddToMenuButton`'s
only caller is `RecipeCard.tsx`; `AddToMenuCTA`'s only caller is
`RecipeHero.tsx`; `AddToMenuStepperControls`/`AddToMenuConfirmButton`/
`AddToMenuBadge`/`useAddToMenuButtonState` are each called by both
`AddToMenuButton` and `AddToMenuCTA`.

Since decision 7 keeps `RecipeCard` in shared `recipes/`, `AddToMenuButton`
has to stay there too — `RecipeCard` hard-imports it as a child, and
moving `AddToMenuButton` to `recipes-browse/` while its parent stays
shared would make the shared folder import from a page-specific one,
exactly backwards. `AddToMenuCTA` has no such constraint: its only
caller, `RecipeHero`, is inherently `recipes-detail/`-only (a recipe
detail hero isn't reusable on another page the way a card is), so it
moves cleanly.

That breaks the folder's original justification, though, not just its
contents. CLAUDE.md's "tight cluster" exception (first applied here at
`CFE-020`) requires the cluster to be self-contained — nothing outside
the folder calling the shared pieces. Once `AddToMenuCTA` sits in a
different top-level feature and reaches back into `recipes/` for
`Stepper`/`Confirm`/`Badge`, the cluster is no longer self-contained by
construction, and the folder's name stops describing its contents (the
detail page's own add-to-menu component isn't in "add-to-menu/"
anymore). Renaming the folder doesn't fix this cleanly — `Stepper`/
`Confirm`/`Badge` are shared by both `AddToMenuButton` *and*
`AddToMenuCTA`, so a name scoped to either one is equally misleading.

Rejected fix: keep the folder, rename it. Chosen fix: flatten it.
`AddToMenuButton.tsx`, `AddToMenuStepperControls.tsx`,
`AddToMenuConfirmButton.tsx`, `AddToMenuBadge.tsx` become flat files in
shared `recipes/components/`, alongside `RecipeCard`/`RecipeCardSkeleton`/
`RecipeFavouriteButton` — 7 files total, nowhere near the scale a
subfolder exists to manage. The `AddToMenu*` name prefix already
signals "these belong together" the same way `Recipe*` does for the
other four; a subfolder was restating that, not adding to it.

### 9. Post-move tree walkthrough surfaced five smaller structural questions, grilled one at a time

After the recipes split shipped, the founder read through the entire
`src/` tree and raised seven questions in one message about adjacent
structure; asked to be interviewed one at a time rather than answered in
bulk. Decisions 10–13 below cover the four that changed anything.
Confirmed as no change needed, not acted on: a `contexts/` grouping for
`AuthContext` (only one real context exists app-wide — one file doesn't
justify a folder); folder-per-component as a default (rejected — a
one-file folder is less scannable than the file alone, and the
`AddToMenu*`/`Recipe*` name prefixes already signal the grouping); and
renaming bare `recipes/` to something like `recipes-shared/` (kept bare,
consistent with `auth`'s bare name for its own cross-cutting layer —
`recipes-browse`/`recipes-detail` reading like sub-folders of it is a
naming-adjacency issue, not evidence the split itself is wrong: merging
`recipes-browse` back into bare `recipes` would put `components/` back
at 19 files, over the same ~15-file threshold that justified the split
in the first place).

### 10. `landing/` gets the `pages/`+`components/` split it should have had since `CFE-003`

It's been flat since `CFE-003` (2026-08-29), before the `pages/`/
`components/`/`hooks/` rule was enforced as strictly as it is now — an
accident of timing, not a deliberate exclusion. Brought into line:
`components/` for `Hero`/`HowItWorks`/`LandingFooter`/`PlannerTease`/
`Pricing`/`PricingCard`/`RecipeCardPlaceholder`/`StepCard`; `styles.ts`
stays loose at root (single-purpose, no bucket, same exception
`auth/googleLogin.ts` gets).

### 11. Single-consumer files in `src/components/` move to live with their actual consumer

`GoogleIcon.tsx` had exactly one consumer (`landing/Hero.tsx`) despite
sitting in the shared bucket — same single-consumer rule applied
throughout this ticket, and it's inherently auth-domain iconography
(pairs with `auth/googleLogin.ts`), so it moved to `features/auth/`.
`RouteFallback.tsx` similarly had one consumer (`AppShell`, in
`components/nav/`) and moved to `components/nav/` — the founder's call
against Claude's initial recommendation (leave it flat, since it's
generic in *nature*), on the reasoning that actual current usage should
win over an abstract "kind of thing" argument.

### 12. `ErrorBoundary`/`ScrollToTop` grouped into a new `components/app/`

Both are mounted only by `App.tsx` itself — root wiring, not reusable
UI, unlike `Logo`/`StatePanel` which have 2+ real feature-level
consumers. Founder's call against Claude's initial recommendation (only
2 files, leave flat) — chosen to make the root-wiring-vs-reusable-UI
distinction explicit in the structure rather than rely on file count
alone.

### 13. `lib/Tanstack/` → `lib/tanstack/` casing fix

Mechanical, no design decision — done via a two-step `git mv` (through a
temporary name) since macOS's case-insensitive filesystem can silently
no-op or confuse git on a case-only rename otherwise. Confirmed tracked
as a clean rename (`git status` showing `R`, not delete+add) before
fixing the 11 external importers.

## Non-goals

- No CFE-008 (My recipes tab) work — this ticket only moves the two
  hooks it'll need; the UI is a future ticket's decision.
- `CLAUDE.md` updated at close-out (2026-09-18), per the feature-folder
  rule's existing precedent (`CFE-004`) of updating it once the move is
  real, not during the grill. Text applied, copied from decisions 1 and
  5 above (plus decisions 9–13's follow-on structure, folded into the
  same update):

  > **Splitting an oversized feature by page.** When a feature's
  > `components/`/`hooks/` bucket exceeds ~15 files *and* splits cleanly
  > by "which routed page exclusively imports this" (mechanical,
  > grep-able — not a by-concern split, which is a judgment call and was
  > rejected at `CFE-004`), split the feature into page-specific sibling
  > features, each with their own `pages/`/`components/`/`hooks/`
  > buckets. Keep only 2+-page-consumer files (including the `data/`
  > singletons) in the original folder as the shared core.
  >
  > Pre-emptively moving a single-consumer file into the shared core
  > (ahead of today's import graph) needs a backlogged ticket that will
  > need it, not a guess. Logic (hooks) is low-risk to move on a single
  > such ticket, since the logic's shape won't change based on who calls
  > it. A presentational component is a real bet on future UI and should
  > wait for its own second real caller *unless* multiple backlogged
  > tickets converge on the same need (e.g. several tabs all needing a
  > recipe-card-shaped display) — that's a stronger signal than one
  > ticket's guess, though the component's internal shape may still need
  > to change once those tickets land; moving it early only answers
  > "where do future tickets find it," not "what will it look like."
  > First applied at `CFE-031` (`recipes/` →
  > `recipes/`+`recipes-browse/`+`recipes-detail/`; `RecipeCard`/
  > `RecipeCardSkeleton` moved pre-emptively on the multi-ticket
  > signal, `useRecipePermissions`/`useDeleteRecipe` on the
  > single-ticket logic case).
  >
  > **The "tight cluster" exception doesn't survive a page split.** If
  > splitting a feature by page pulls one of a shared sub-component
  > cluster's parent callers into a different top-level feature, the
  > cluster is no longer self-contained (the exception's own
  > requirement) and any folder built around it should be flattened
  > rather than renamed — a name scoped to either remaining caller ends
  > up equally misleading once the cluster is reached into across a
  > feature boundary. First applied at `CFE-031`: `recipes/components/
  > add-to-menu/` (built at `CFE-020`) dissolved once `AddToMenuCTA`
  > moved to `recipes-detail/`, leaving `AddToMenuButton` and its three
  > shared sub-pieces flat in shared `recipes/components/`.
  >
  > **Fourth bucket: `data/`.** A feature's `api.ts`/`types.ts`/
  > `queryKeys.ts` singleton files live in a `data/` subfolder, not
  > loose at feature root. Strictly these three file kinds — a genuine
  > one-off file with no natural bucket (e.g. `auth/googleLogin.ts`)
  > still stays loose per the existing exception. Applies to every
  > feature from its first ticket forward. Retrofitted to `auth/`,
  > `menu/`, `recipes/` at `CFE-031`.
- No behavior, route, or visual changes — this is a pure reorg.

## Verification

Mechanical reorg, no new logic/API/visual/interactive surface — the
check is structural integrity, run after the move (not batched at the
very end; check after each commit per the global one-commit-per-unit
rule):

- `tsc -b` — the whole-solution build. **Not** `tsc --noEmit -p .`,
  which silently no-ops on this solution-style tsconfig (the exact
  mistake `CFE-004`'s own reorg made — `LESSONS.md` 2026-09-05).
- `npx vitest run` — full suite, confirms every relocated test still
  finds its subject via the updated relative/`@/` import.
- A manual grep for `vi.mock(` targets referencing old
  `@/features/recipes/...` paths — `CFE-004`'s lesson notes a
  find-and-replace regex over `from "..."` imports never touches
  `vi.mock()` strings, so this needs a separate pass.
- `npm run lint` — confirms no new import-resolution or a11y regressions.
- `npm run build` — confirms `AppRoutes.tsx`'s lazy-loaded chunk imports
  (`BrowseRecipesPage`, `RecipeDetailRoute`) still resolve post-move,
  no chunk-size regression.

Suggested commit sequence (smallest reversible step per commit,
founder's call to reorder): (1) `data/` bucket retrofit for `auth/` and
`menu/` — no cross-feature risk, good warm-up; (2) `data/` bucket for
`recipes/` alone, still flat otherwise; (3) carve out `recipes-browse/`;
(4) carve out `recipes-detail/` — including the two pre-emptive hook
moves, moving `AddToMenuCTA` out, and flattening what's left of
`add-to-menu/` (`AddToMenuButton`/`Stepper`/`Confirm`/`Badge`) into
`recipes/components/`; (5) `landing/`'s and `menu/`'s `pages/` bucket +
`MenuPage` rename. Run the verification block after each.

Actually run as two batches (data/recipes split, then the decision
9–13 follow-on cleanup), each verified against the full gate above
(`tsc -b` clean, 258/258 tests, 16 pre-existing lint warnings — no new
ones, `build` producing the same chunk breakdown) before moving on.
Interactive check (`npm run dev`, clicking through `/`, `/recipes`,
`/recipes/:id`, `/menu`, login) confirmed by the founder at close-out.
