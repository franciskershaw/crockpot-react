# CFE-014 — Admin recipe approval

Admins get a Pending tab in Library and an Approve button on a pending
recipe's detail page, calling `crockpot-go` `CROC-017`. Also fixes the
missing frontend side of `CROC-062`: owners lose Edit/Delete once their
recipe is approved. Grilled 2026-10-09 together with `CROC-017`
(`crockpot-go/docs/handoffs/CROC-017.md`). Cheap to undo.

**Implementation mode**: AI-driven.

## Facts this rests on (checked 2026-10-09)

- Library sub-tabs are the static `LIBRARY_TABS`
  (`src/features/your-crockpot/utils/yourCrockpotTabs.ts:7-10`), rendered
  by `LibraryTabs` with counts from `YourCrockpotLayout.tsx:80-85`
  (`TabCount`). Routes at `src/app/AppRoutes.tsx:143-163`.
- `useMyRecipes` (`your-crockpot/hooks/useMyRecipes.ts`) is the list-hook
  template: `useApiInfiniteQuery`, keyed `recipeKeys.list(PARAMS)` under
  `recipeKeys.lists()`, `LIBRARY_PAGE_SIZE`. `listRecipes` maps `mine`
  at `recipes/data/api.ts:38`.
- The pending banner shows to the owner only (`isOwnPendingRecipe`,
  `RecipeDetailPage.tsx:55`). An admin sees nothing marking a recipe as
  pending. The banner is `recipes-detail/components/RecipePendingApprovalBanner.tsx`.
- The hero renders the photo directly below the banner
  (`RecipeHero.tsx:64-66`).
- `canManageRecipe` (`recipes/hooks/useRecipePermissions.ts:6-12`) is
  admin-or-owner, ignoring `approved`. It gates hero Edit/Delete
  (`RecipeHero.tsx:43`) and the edit route (`EditRecipePage.tsx:73-75`).
  `EditRecipePage.tsx:26` shows "Saving sends this back for approval",
  but since `CROC-062` the backend returns `403 recipe_approved_locked`
  instead.
- No screenshot covers any admin or pending state.

## Decisions

1. **Pending tab in Library**, third after Favourites / My recipes, at
   `/library/pending`. `LIBRARY_TABS` is filtered by role so non-admins
   never see it, and a non-admin who opens the URL is redirected to
   `/library/favourites`. Shows a count via `TabCount`. The Library
   subtitle is unchanged.
2. **`usePendingRecipes`** copies `useMyRecipes` with `{ approved: false }`,
   enabled only for admins, keyed under `recipeKeys.lists()`.
   `listRecipes` gains an `approved?: false` param.
3. **Admin banner variant**: same strip and tokens as the owner banner,
   copy "Pending approval — check the photo and details before
   approving", stock shadcn `Button` "Approve" on the right, disabled
   while the request is in flight. Shown when `user.role === "ADMIN" &&
   !recipe.approved`. Built without a spec dump (existing tokens + stock
   button); shown on screen before wiring.
4. **`useApproveRecipe`** sends the loaded `recipe.updatedAt`. On 200 it
   writes the returned detail into `recipeKeys.detail(id)` (banner goes),
   invalidates `recipeKeys.lists()` (leaves Pending), and toasts
   "Approved". On `409 recipe_changed` it refetches the detail, and the
   banner shows "This recipe changed since you opened it — check it
   again" until the next approve attempt. Any other error toasts as usual.
5. **CROC-062 pair folded in**: `canManageRecipe` = admin, or owner while
   `!approved`. The `losesApproval` footnote goes. The existing edit-route
   guard then redirects owners of approved recipes.
6. **No bulk approve, no admin dashboard, no pending badge on browse
   cards.**

## Acceptance criteria

- [ ] `canManageRecipe` truth table: admin × {pending, approved} → true;
      owner pending → true; owner approved → false; other user → false;
      signed out → false.
- [ ] Owner of an approved recipe sees no Edit/Delete, and `/recipes/:id/edit`
      redirects to the detail; the "sends this back for approval" note is
      gone.
- [ ] Pending tab visible only to admins, lists pending recipes with a
      count, empty state "Nothing waiting for approval"; non-admin URL
      access redirects to favourites.
- [ ] Admin on a pending recipe sees the admin banner with Approve; the
      owner still sees their existing banner; anyone on an approved recipe
      sees neither.
- [ ] Approve success: banner gone without reload, recipe leaves the
      Pending tab, toast shown.
- [ ] Approve 409: detail refetched, changed-copy shown, a second approve
      against the fresh `updatedAt` succeeds.
- [ ] Approve button disabled while the request is in flight (no double
      submit).

## Non-goals

- Reject/un-approve, rejection reasons (backend non-goal).
- Pending badges on browse or My recipes cards.
- Image moderation. If public signup opens wide, consider a Cloudinary
  moderation add-on on `crockpot-go`'s upload (`CROC-040`); check pricing.
- Moving the recipe reference-data query keys (`CFE-043`).
