## Medium severity

### 1. No error boundary anywhere in the app

**File**: `src/app/App.tsx`, `src/app/AppRoutes.tsx`

Grepped the whole `src/` tree for `ErrorBoundary`/`errorElement` — zero
matches. Any unhandled render-time exception (a null-pointer bug in a new
component, a bad prop shape from an API response) white-screens the
entire SPA with no fallback UI and no recovery path short of a manual
reload.

**Why it matters**: cheap to add now, before more screens land and the
blast radius of any one component's bug grows. Not urgent at 4 shipped
routes, but the fix is a single boundary and gets more valuable with
every ticket that ships after it.

**Fix**: one top-level `ErrorBoundary` in `App.tsx`, or per-route
`errorElement`s via `react-router`'s data APIs if that migration ever
happens — either is a small, self-contained change.

**Ticket**: `CFE-016`.

### 2. No retry/error UI for failed queries — only a toast

**Files**: `src/features/recipes/components/RecipeGrid.tsx:65-67`
(`if (!data) return null;`), `src/features/recipes/components/FilterPanel.tsx:32-49`
(`categoriesQuery.data ?? []`, `itemsQuery.data ?? []`,
`timeRangeQuery.data && ...`); the underlying wrappers,
`src/lib/Tanstack/useApiQuery.ts:22-31` and
`src/lib/Tanstack/useApiInfiniteQuery.ts:44-53`, surface a failure as a
transient `sonner` toast and nothing else.

Once the toast fades, the browse grid renders permanently blank and the
filter panel silently renders as if there were zero categories/
ingredients/no time bounds — indistinguishable from "still loading" or
"genuinely empty," with no retry affordance.

**Why it matters**: any network blip or backend 5xx while a visitor is on
`/recipes` — the one real page in the app today — leaves them looking at
an empty grid with no way to tell what happened or try again short of a
manual refresh.

**Fix**: surface `isError`/`error` from these query hooks in the
components themselves (a retry button + short message), not just via the
shared toast side-effect.

**Ticket**: `CFE-016`.

### 3. `client.ts`'s token-refresh/retry logic is untested

**Files**: `src/lib/http/client.ts:16-39` (singleton `refreshPromise`
collapsing concurrent 401s), `:57-60` (retry-once-then-fail);
`src/lib/http/client.test.ts` (existing coverage: 204 handling and
error-body parsing only).

No test exercises concurrent 401s collapsing to one refresh call, the
retry-once behavior, or what happens when `performRefresh` itself fails
mid-request. On inspection the mechanism reads correctly (singleton
promise, `hasRetried` flag prevents infinite retry) — this is a coverage
gap, not a live bug.

**Why it matters**: this is the highest-consequence code in the HTTP
client — the project's own testing guidance (`CLAUDE.md`) flags exactly
this class of logic ("real branching/state transitions/edge cases a
refactor could silently break") for coverage, and a regression here means
either a refresh thundering-herd or a silent auth loop for every user at
once.

**Fix**: add tests for concurrent-401 collapse, retry-once-then-fail, and
`performRefresh` failure, alongside the existing `client.test.ts` cases.

**Ticket**: `CFE-017`.

### 4. `useLogout` bypasses the shared error-toast wrapper

**Files**: `src/features/auth/hooks/useLogout.tsx:7-17` (raw
`useMutation` from `@tanstack/react-query`), vs.
`src/features/recipes/hooks/useToggleFavourite.ts:34-53` and every other
mutation in the codebase, which goes through
`src/lib/Tanstack/useApiMutation.ts` (toasts on failure).

`useLogout`'s `onSettled` unconditionally clears the token and session
cache regardless of whether the server-side `/auth/logout` call actually
succeeded — correct behavior (the user should end up logged out
client-side either way) — but because it skips `useApiMutation`, a failed
network call produces no toast telling the user anything went wrong
server-side.

**Why it matters**: drift between a CFE-002a-era hook and the
CFE-004-era shared pattern; low risk today, but the next person editing
this hook has no signal that it diverges from the rest of the codebase's
mutation convention.

**Fix**: route the logout mutation through `useApiMutation` (or
explicitly document why it's exempt, if the silent-toast behavior is
actually intentional here).

**Ticket**: `CFE-017`.

## Low severity

### 5. Import-style drift between early and late code

**Files**: `src/features/auth/hooks/useLogout.tsx:3,5`,
`src/features/auth/pages/AuthCallback.tsx:5`,
`src/features/menu/MenuScreen.tsx:1-3` — deep relative imports
(`../../../lib/http/tokenStore`, `../../../app/routes`,
`../../components/ui/button`) crossing feature boundaries, vs. the rest
of the codebase (37 files), which consistently uses the `@/` path alias
configured in `vite.config.ts`.

All three offending files date from `CFE-001`/`CFE-002a`, before the
alias convention took hold in `CFE-003`/`CFE-004` work.

**Why it matters**: purely cosmetic today, but deep relative imports are
more brittle under the feature-folder reorg pattern this project already
applies (`CLAUDE.md`'s hard rule) — a future file move breaks them
silently in a way `@/` imports don't.

**Fix**: mechanical find-and-replace to `@/...` in the three files,
verified with the project's real build/typecheck command per this
project's own `CFE-004` lesson (a plain regex swap isn't enough
verification on its own).

**Ticket**: `CFE-019`.

### 6. Duplicated toast-error-wrapping boilerplate

**Files**: `src/lib/Tanstack/useApiQuery.ts:21-32`,
`src/lib/Tanstack/useApiInfiniteQuery.ts:44-53`,
`src/lib/Tanstack/useApiMutation.ts:15-18`.

Each of the three independently repeats the identical
`error instanceof ApiError ? error.message : "request failed"` ternary
and toast call.

**Why it matters**: three copies of the same logic can drift — e.g. a
future i18n/wording update lands in one and not the other two.

**Fix**: a single shared `apiErrorMessage(error)` helper (or a common
`withErrorToast` wrapper), reused by all three.

**Ticket**: `CFE-018`.

### 7. Redundant Radix dependency + inconsistent import source

**Files**: `package.json:17,26` (`@radix-ui/react-slot@^1.3.3` alongside
the unified `radix-ui@^1.6.7`, which itself depends on the same
`@radix-ui/react-slot@1.3.3` — confirmed via
`node_modules/radix-ui/package.json`); `src/components/ui/button.tsx:3`
imports `Slot` from the standalone `@radix-ui/react-slot` package
directly, while every other shadcn primitive (`badge.tsx:4`,
`checkbox.tsx:4`, `dialog.tsx:5`, `dropdown-menu.tsx:4`) imports its
Radix primitive from the unified `radix-ui` package instead.

**Why it matters**: versions match, so this doesn't currently duplicate
in the shipped bundle — it's an unnecessary explicit dependency and an
inconsistent convention across otherwise-identical shadcn-generated
files, nothing more.

**Fix**: drop the standalone `@radix-ui/react-slot` dependency, import
`Slot` from `radix-ui` in `button.tsx` to match the other four files.

**Ticket**: `CFE-019`.

### 8. `FilterPanel` re-fetches reference data `BrowseRecipesPage` already fetched

**Files**: `src/features/recipes/pages/BrowseRecipesPage.tsx:30-31`
(calls `useRecipeCategories()`/`useItems()`, passes results to
`FilterPills` as props) vs.
`src/features/recipes/components/FilterPanel.tsx:32-34` (independently
calls `useRecipeCategories()`, `useItems()`, and `useRecipeTimeRange()`
again rather than receiving them as props).

**Why it matters**: TanStack Query's cache (same query key, 1hr
`staleTime`) means this doesn't cause a duplicate network request today
— but it's two separate call sites for the same data that could silently
diverge if a future `staleTime` or `select` override lands on one and not
the other.

**Fix**: thread the already-fetched data into `FilterPanel` as props,
same pattern already used for `FilterPills`.

**Ticket**: `CFE-018`.

### 9. No image lazy-loading in an infinite-scroll grid

**File**: `src/features/recipes/components/RecipeCard.tsx:29-33` — the
recipe `<img>` has no `loading="lazy"` attribute.

`RecipeGrid.tsx` is an `IntersectionObserver`-driven infinite-scroll
list, so every newly-mounted page of cards fetches its images eagerly the
moment React mounts them, rather than only once genuinely near the
viewport.

**Why it matters**: minor at the current catalog size; worth fixing
before the catalog (and the number of cards mounted per scroll session)
grows.

**Fix**: add `loading="lazy"` to the `<img>` — one line.

**Ticket**: `CFE-019`.

### 10. No route-based code splitting *(carried forward from 2026-09-04)*

**File**: `src/app/AppRoutes.tsx` — see
`docs/findings/2026-09-04-tech-debt.md` for full detail (every route
imported eagerly; `motion`, used only by `RecipeGrid.tsx`, pushed the
prod build past Vite's 500KB chunk-size warning — 602KB unminified /
193KB gzipped). Deliberately deferred at `CFE-004` (2026-09-04); still
open.

**Ticket**: `CFE-019`.
