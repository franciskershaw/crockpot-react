# CFE-047 — Browse filters: hide household items, show loading instead of "0 results"

Browse's ingredient filter drops items in non-ingredient categories (House),
filtering the shared `useItems` list on the frontend. Its filter sections and
ingredient pills show skeletons while their data is pending, instead of
"0 results" and missing pills. Grilled 2026-10-03. Cheap to undo.

**Implementation mode**: AI-driven.

## Facts this rests on (checked 2026-10-03)

- The recipe form's search already filters client-side:
  `AddItemSearch.tsx:77` runs `ingredientItems(items, categories)` for
  `variant === "recipe"`. Browse is the only remaining place that lists House
  items as ingredients.
- `useItems` is one cached query (`catalogKeys.items`,
  `REFERENCE_DATA_STALE_TIME` = 1h, `lib/constants.ts:2`). Its consumers are
  browse filter + pills, recipe search, `IngredientsSection`'s `itemsById`,
  and the shopping-list search.
- House has 29 of 387 items (`crockpotV3.Item.json`). `GET /items` is
  126 KB uncompressed in the network tab (local dev).
- `FilterPanel` passes `categoriesQuery.data ?? []` / `itemsQuery.data ?? []`
  and handles only `isError`, so a pending query renders as empty.
  `FilterOptionList` then shows "0 results". The time range renders only
  when `timeRangeQuery.data` is present, so it has no pending state.
- `FilterPills.tsx:73` skips an ingredient id it can't resolve, so a URL with
  `ingredientIds` shows filtered recipes but no pill until items arrive.
- `FilterOptionList` shows `INITIAL_VISIBLE_COUNT` = 6 rows before "Show All".
- Existing skeleton pattern: `RecipeCardSkeleton.tsx` (`aria-hidden`,
  `animate-pulse`, `bg-muted` blocks, `rounded`).
- No design screenshot covers a loading state (`../screenshots/browse/` has
  only `browse1.png`, `browse2.png`).

## Decisions

1. **The frontend filters; `GET /items` is unchanged.** A
   `?ingredient=true` variant would add a second cached list (the full
   catalogue downloaded twice by anyone using browse and the shopping list),
   to save 29 rows. It also does nothing for load time, which `crockpot-go`
   `CROC-045` addresses with gzip. Revisit if non-ingredient categories grow
   into a large share of the catalogue.
2. **Pills resolve names from the full list**, not the filtered one, so a
   stale `ingredientIds` for a House item still shows a removable pill.
3. **Recipes keep loading independently of the filters.** The grid is the
   main content. Waiting on the 126 KB items list would slow every load.
4. **Per-section skeletons while pending.** Categories and Ingredients keep
   their real `h3` heading and show 6 placeholder rows. The search input and
   "Show All" are hidden. The time range shows one placeholder bar the height
   of the slider block. They only show on a cold load: the cache lasts 1h.
   *Added while building:* placeholders use `DELAYED_FADE_IN_CLASSES`
   (`lib/styles.ts`, invisible for 200ms) and an sr-only `<output>` label,
   as `LibraryListSkeleton` does, so a fast load never shows them.
5. **Placeholder pill per unresolved ingredient id while items are
   pending.** Once items have loaded, an id that still doesn't resolve is
   skipped as it is today. *Added while building:* category pills had the
   same gap and get the same placeholder while recipe categories are
   pending.
6. **No Claude-Design spec dump.** The skeletons reuse only existing styling:
   `RecipeCardSkeleton`'s `animate-pulse` + `bg-muted` + `rounded`,
   `FilterOptionList`'s row metrics (`px-2 py-1`, `gap-2.5`, checkbox-sized
   square + text-height bar of varying width), and the existing pill's shape.
   No new typography or shadows means nothing for a spec to pin down.
7. **Prefetching items at app start is out.** It costs 126 KB for users who
   never open browse or the recipe form. Revisit after gzip if cold browse
   loads still feel slow.

## Non-goals

- Any `GET /items` change (gzip is `crockpot-go` `CROC-045`).
- Pagination or server-side search of items.
- Pending states on other screens (recipe form, shopping-list search).

## Acceptance criteria

- [ ] Browse's ingredient filter lists no item from a category with
      `isIngredient: false`. Every other item is still listed.
- [ ] An `ingredientIds` URL param naming a House item still shows a
      removable pill with its name.
- [ ] While categories are pending, the Categories section shows a skeleton,
      not "0 results". The same goes for Ingredients.
- [ ] While the time range is pending, its placeholder bar shows.
- [ ] While items are pending, each `ingredientIds` entry shows a placeholder
      pill. Once they load, the real pills replace them.
- [ ] Errors still show `InlineRetry` as today.
- [ ] Desktop panel and mobile drawer both behave as above.

## Pieces and verification

Each piece: failing tests first, stop at red, then green, then stop.

1. **Ingredient filter excludes House** (logic). `BrowseRecipesPage` adds
   `useItemCategories()` and passes `ingredientItems(...)` to the filter
   panel. Pills still get the full list. Vitest: a House-flagged category's
   items are absent from the ingredient filter and present elsewhere. A
   House id in the URL still renders its pill.
2. **Pending states** (logic + visual). `FilterPanel` branches on
   `isPending` per section. `FilterPills` takes a pending flag for items.
   Vitest: a pending query renders the skeleton and no "0 results". Pending
   items render one placeholder pill per id. Then the founder's look:
   `npm run dev` + local `crockpot-go`, DevTools throttled to "Slow 4G" with
   cache disabled, desktop panel and mobile drawer. Check that the layout
   matches `browse1.png`/`browse2.png` once loaded and doesn't jump when data
   lands.

Commands: `npm test`, `npm run lint`, `npm run build`, then `branch-review`
before close-out.
