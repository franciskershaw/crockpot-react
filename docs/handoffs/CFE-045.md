# CFE-045 — Menu write errors show copy, not codes

A menu write refused with `menu_limit_reached` or
`shopping_list_quantity_too_large` reverts as it does today and toasts a
readable message instead of the raw code. Paired with `crockpot-go`
`CROC-059` (cap of 30, `docs/handoffs/CROC-059.md` there), grilled
together 2026-10-09. Also takes the menu half of `CFE-054` (2). Cheap to
undo.

**Implementation mode**: AI-driven.

## Facts this rests on (checked 2026-10-09)

- Every menu write — add, serves change, remove, clear — goes through
  `useOptimisticMenuMutation` (`features/menu/hooks/`), which already
  reverts the optimistic change on error.
- All four add surfaces (`AddToMenuButton`, `AddToMenuCTA`,
  `MobileRecipeRow` via `useAddToMenuButtonState`, and the Menu tab's undo
  via `useUndoableMenuRemoval`) call `useAddToMenu`.
- `useApiMutation` toasts `apiErrorMessage(error)` unless
  `isHandledError` claims it; `ApiError.message` is the server's code, so
  today these errors toast "menu_limit_reached".
- Precedent: `createRegularErrorCopy.ts` (code → copy map, 409 only) +
  `isHandledError` in `useCreateRegular.ts:14`.
- `crockpot-go` returns `shopping_list_quantity_too_large` (400) from all
  four menu writes (`menu_handler.go:70, 105, 140, 175`).

## Decisions

1. **No pre-disable at the cap.** The cache can be stale across
   tabs/devices, so the 409 path is needed regardless; a disabled state on
   four surfaces has no design and would block on a spec dump for a cap
   no real user should reach. The add flickers in and reverts.
2. **Toast, with copy.** It's the existing error channel for every menu
   surface and the only one that still exists after an undo tile closes.
   - `menu_limit_reached`: "You've reached the 30-recipe menu limit.
     Remove one to add another." (mirrors the regulars line)
   - `shopping_list_quantity_too_large`: "That would push a shopping-list
     quantity past the largest amount we can store." (placeholder wording)
3. **Mapping lives in the shared hook.** `features/menu/utils/menuErrorCopy.ts`
   matches on status + code like `createRegularErrorCopy`;
   `useOptimisticMenuMutation` passes `isHandledError: (e) =>
   menuErrorCopy(e) !== null` and calls `toast.error(copy)` in its
   `onError` alongside the revert. Covers all four writes in one place.

## Acceptance criteria

- [ ] A `409 menu_limit_reached` on add reverts the optimistic entry and
      toasts the limit copy, once.
- [ ] A `400 shopping_list_quantity_too_large` from any menu write toasts
      its copy, once.
- [ ] Any other error still toasts as today, once.
- [ ] On screen: browse card, detail CTA, mobile row and undo re-add each
      show the add, revert it, and show the limit toast on a full menu.

## Non-goals

- Disabling add before the request.
- Showing the cap or a count anywhere in the UI.
- Reading the cap from the server: the copy hardcodes "30", so changing
  `crockpot-go`'s `maxMenuEntries` means editing this copy too. Accepted
  for a constant that rarely moves.
- The rest of `CFE-054` (`parseQuantity` ceiling, shopping-list codes).

## Verification

- **Logic** (failing tests first): hook tests in
  `useOptimisticMenuMutation.test.tsx` / `useAddToMenu.test.tsx` and a
  `menuErrorCopy` unit test — `npx vitest run src/features/menu`.
- **Interactive** (founder, after `CROC-059` lands): fill the menu to 30
  with the backend's script, then try an add from the browse card, the
  detail-page CTA and the mobile row (narrow window); each shows the add,
  reverts, toasts. Undo: on a full menu remove an entry, add a different
  recipe from browse, return and press undo — the restore fails with the
  toast.
