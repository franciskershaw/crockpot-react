## Summary

Build `/recipes` for real: a filter panel (cooking-time range, category
include/exclude, ingredient search) + name search, an infinite-scroll
recipe card grid, and a favourite toggle — replacing
`RecipesComingSoon`. Also builds the shared `AppShell` (one nav, mounted
on every route, branching on auth state) that every screen from here on
mounts inside, since neither `SiteHeader` nor `MobileTabBar` had an
authenticated branch yet.

**Cross-repo dependency**: the time-range slider needs real min/max
cooking-time bounds. `crockpot-go` has no such endpoint today (the old
app got this from a live Prisma aggregate,
`getRecipes.ts:74-99` — `crockpot-go` has nothing equivalent). **New
ticket `CROC-043`** (small: one aggregate query + endpoint, its own
grill) is a prerequisite for the slider specifically — added to
`crockpot-go`'s Epic 4 backlog. Everything else in this ticket has no
backend gap.

## Decisions and why

### 1. One `AppShell`, mounted on every route — `SiteHeader`/`MobileTabBar` branch internally on auth state

**Corrected mid-build (2026-09-02)** — the first pass of this ticket
built `AppShell` as a *separate* header/tab-bar pair, mounted only
behind `RequireAuth`, leaving the existing `SiteHeader`/`MobileTabBar`
as a wholly separate logged-out-only pair. That's two parallel nav
systems, caught by checking the old app directly
(`crockpot/src/app/layout.tsx` + `components/layout/navigation/Navbar.tsx`):
it has **one** `Navbar` and **one** `BottomMobileNav`, mounted once in
the root layout for every route, each branching internally on
`useSession()` status. It also contradicted this project's own prior
decision (`docs/handoffs/CFE-003.md`: *"CFE-006 adds the `useAuth`
branch ... and hoists it into the `AppShell` layout route"* — i.e.
`SiteHeader` was always meant to grow the branch itself, not be
shadowed by a sibling component).

Corrected shape, matching the old app:

- `src/components/nav/AppShell.tsx` — a layout component (`<Outlet />`,
  `react-router-dom` v7) rendering `SiteHeader` + `<Outlet/>` +
  `MobileTabBar`, wrapping **every** route (`/`, `/auth/callback`,
  `/recipes`, `/menu`, the catch-all) via one top-level `<Route
  element={<AppShell />}>` in `AppRoutes.tsx`. `RequireAuth` still
  guards `/menu`'s *content* (redirects an anonymous visitor away from
  it) — it no longer decides which nav renders.
- `SiteHeader`/`MobileTabBar` each branch on `useAuth().isAuthenticated`
  internally. **Logged out, on every route** (confirmed at the
  interview — a fixed set, not conditional on which page you're on):
  Recipes, How it works, Pricing, Sign in. **Logged in, on every
  route**: Browse recipes, Your Crockpot, Add a recipe (disabled), the
  account avatar/logout menu. No cart/shopping-list badge in either
  state — that needs CFE-009's data and isn't built yet.
- "Add a recipe" nav link and any "Add Recipe" CTA are **non-functional
  placeholders** (`AddRecipeLink`, disabled with `aria-disabled` +
  "Coming soon" tooltip) until CFE-010 ships — matches how `/recipes`
  itself was stubbed at CFE-003 for exactly this reason.
- **"How it works"/"Pricing" work from any route, not just `/`** — per
  the interview, the logged-out nav must be identical everywhere, and
  removing anchor links off the landing page would make the nav shape
  page-dependent again. They're now `<Link to="/#how-it-works">` /
  `<Link to="/#pricing">` (not plain `<a href="#...">`, which only works
  when already on the target page) plus a small `useScrollToHash` hook
  (`src/lib/useScrollToHash.ts`, watches `useLocation().hash`) mounted
  once in `LandingPage`. Handles both cases uniformly: navigating from
  elsewhere lands on `/` with the hash already set (effect fires on
  mount); clicking from `/` itself changes the hash without a remount
  (effect fires on the `hash` dependency change).
- `LandingPage` no longer mounts its own `SiteHeader`/`MobileTabBar` —
  the shared `AppShell` supplies them now. It keeps `LandingFooter`
  landing-local, per CFE-003's original decision.

### 2. Recipe card: heart only, no cart/add-to-menu action

`browse1.png` (desktop) shows a per-card cart icon (quick add-to-menu)
next to the heart; `browse2.png` (mobile) has neither — only an
unrelated floating global cart badge. The two mockups already disagree,
and there's nothing to wire it to: `crockpot-go`'s menu-add endpoint
(`CROC-019`, `POST /menu/entries`) has no `Done` marker and no handoff —
still just a backlog line. Ship the card with just the favourite heart;
add the cart action once `CROC-019` gives it a real contract to call
(likely CFE-006, extending this same card component).

### 3. Favourite heart: hidden entirely for anonymous visitors

`POST /recipes/:id/favourite` is full-auth, 401 for anonymous
(`CROC-018` decision 2). Rather than showing a heart that redirects to
login on click, the card renders with **no favourite affordance at all**
when `useAuth().isAuthenticated` is false — avoids a click that can't
succeed. Matches the old app's own gating
(`RecipeCard.tsx:137-138`: `showActions = status === "authenticated"`).

### 4. Favourite toggle: optimistic update against the card's own cache entry, not a separate favourites list

The old app (`AddToFavouritesButton.tsx`, `useFavourites.tsx`) held a
separate full favourites-list query and cross-referenced each card's id
against it — because its backend's list endpoint never told you
`isFavourite` per card. **Don't port that.** `crockpot-go`'s `RecipeCard`
DTO now carries `isFavourite` directly (`CROC-018` decision 7). The
mutation (`useApiMutation`-wrapped `POST`/`DELETE
/recipes/:id/favourite`) does an optimistic `queryClient.setQueryData`
flip of that one card's `isFavourite` inside the active
`useInfiniteQuery` cache, with rollback in `onError` — precise per-card
state, no second list fetch, no cross-referencing.

### 5. Pending-recipe badge — moved off the browse card to the recipe detail page

**Corrected (2026-09-04):** this ticket originally rendered a small muted
"Pending approval" badge on `RecipeCard` next to the category badges
when `approved === false` (`CROC-015` decision 2, `approved` field
exists on the card DTO "so they know which"). Founder's call: drop it
from the browse card entirely — `RecipeCard` renders no pending-state UI
at all now — and surface it instead as a highlighted element on the
recipe detail page, which is `CFE-005`'s responsibility, not this
ticket's. A logged-in user's own unapproved recipe still appears inline
in their own browse results exactly as before (`CROC-015` decision 2,
unchanged) — it just carries no visual distinction on the card anymore;
that explanation now lives one click away on the detail page instead.
Never shown to any other viewer either way (backend visibility already
guarantees nobody else's browse or detail view includes it).

### 6. Filter state lives in the URL, not localStorage

The old app persisted filters to localStorage
(`FilterProvider.tsx:39-63`) — not shareable, not bookmarkable, and
orthogonal to `react-router-dom` v7's idiomatic `useSearchParams`. CFE-004
uses URL search params instead: `?q=&categoryId=&categoryMode=&ingredientId=&minTime=&maxTime=`
map directly onto `CROC-015`'s filter vocabulary, the URL is shareable,
back/forward moves between filter states, and the query string doubles
as the TanStack Query cache key with no extra context provider needed.
Trade-off accepted: filters reset to empty on a fresh visit rather than
remembering last session's — acceptable for a browse feed.

### 7. Pagination: infinite scroll, `useInfiniteQuery`

`CROC-015`'s offset pagination was explicitly designed for this
(`getNextPageParam: p => p.page < p.totalPages ? p.page + 1 : undefined`,
per its handoff). Ported from the old app
(`RecipeGrid.tsx`): an `IntersectionObserver` on a sentinel div,
`rootMargin: "200px 0px"` (fetch before the user hits bottom), a 500ms
re-trigger debounce. New: needs a `useApiInfiniteQuery` wrapper
(mirroring `useApiQuery`'s toast-on-error shape,
`src/lib/Tanstack/useApiQuery.ts`) — doesn't exist yet, small addition.

### 8. Cascade-in animation, new `motion` dependency

Per interview: "infinite scroll, with a nice animation that sort of
makes it look like they're cascading in from the left to right" — this
matches the old app's `RecipeGrid.tsx:206-216` exactly (`motion/react`,
per-card `initial={{opacity:0,y:20}}` → `animate`, delay staggered by
grid index, `Math.min(index * 0.03, 0.3)` for the initial page and
`newItemIndex * 0.08 + 0.1` for newly-loaded pages). `motion` is **not**
currently a dependency of `crockpot-react` (checked `package.json`) —
add it fresh, matching the version family the old app used (`^12.x`),
not pinned to its exact old version.

### 9. Reference-data fetching: `GET /items` and `GET /recipe-categories` are bare, unpaginated, unsearchable

Both confirmed public with no query/search param
(`crockpot-go/internal/handler/item_handler.go:38-44`,
`main.go:129,159`). 28 seeded categories
(`000006_seed_recipe_categories.up.sql`), items catalog is small (~387
in the old Mongo export). Fetch each once client-side, filter/search
**client-side** in the filter panel (matches the old app's
`GenericFilterList.tsx` — search-within-list, "Show all (N more)"
expansion past 6 visible). Cache with a long `staleTime` — both lists
are admin-write-only and change rarely.

### 10. Time-range slider bounds — blocked on `CROC-043`

See Summary. Until `CROC-043` ships, this piece of the ticket is
blocked — sequence it last in the roadmap below, not first.

### 11. No relevance ranking, no random ordering

`CROC-015` ships `created_at DESC` only; random/relevance ordering is
explicitly `CROC-042`'s job, not shipped. The browse grid will look
different from the old app (date order, not shuffled/scored) until
`CROC-042` lands — an accepted, already-decided backend scope split, not
a new decision here. No relevance badges, no "N ingredients matched"
chips (`RecipeCard.tsx:250-275` in the old app) — nothing in `CROC-015`'s
DTO backs them.

### 12. Recipe card links to `/recipes/:id`, which doesn't exist yet

`AppRoutes.tsx` has no `/recipes/:id` route — `CFE-005` adds it. Cards
link there anyway (`<Link to={`/recipes/${id}`}>`); until CFE-005 ships,
that 404s into the catch-all `*` → `/`. Acceptable since CFE-005 is next
in sequence — not worth a stub detail page for one ticket's gap.

### 13. No "mine"-only filter control

Backend visibility already surfaces a user's own pending recipes inline
automatically (decision 5 above) — no separate "my recipes" toggle in
the public browse filter panel, matching the old app (no such control in
`Header.tsx`/`MobileFilterSidebar.tsx`). A dedicated my-recipes view is
`CFE-008`'s tab, not this page.

### Astro-migration constraint (master spec, still applies)

Recipe list/detail data-fetching goes through a plain async function
(`src/features/recipes/api.ts`: `listRecipes(params)`,
`getRecipeTimeRange()`) that `useInfiniteQuery`/`useQuery` wrap — not
written inline in the hook. Keep the page component thin on
`react-router`-specific hooks beyond `useSearchParams` (needed for
filter state, decision 6 — an acceptable, previously-flagged exception
since filters are inherently URL-shaped).

## Acceptance criteria

- [ ] `AppShell` wraps every route via one top-level layout route.
      `SiteHeader`/`MobileTabBar` branch on `useAuth().isAuthenticated`:
      logged out → Recipes/How it works/Pricing/Sign in everywhere;
      logged in → Browse recipes/Your Crockpot/Add a recipe (disabled)/
      avatar+logout everywhere. No cart badge either state.
- [ ] "How it works"/"Pricing" navigate-then-scroll correctly from any
      route, not just `/`.
- [ ] Search box (name, `q` param), 300ms debounce (`SearchBar.tsx`
      pattern).
- [ ] Category filter: include/exclude toggle, search-within-list,
      6-visible + "Show all (N more)" expansion, checkboxes reflect URL
      state.
- [ ] Ingredient filter: search-within-list, same visible/expand pattern,
      OR-combined with category-include per `CROC-015`.
- [ ] Time-range slider: dual-handle, 5-min step, 300ms debounce —
      **wired last**, blocked on `CROC-043`.
- [ ] Active-filter pills row with individual remove (×) + "Clear all",
      desktop inline / mobile inside the "Filters (N)" drawer trigger.
- [ ] Mobile: full-screen filter drawer (`MobileFilterSidebar.tsx`
      pattern) — focus trap, `Escape` closes, closes automatically past
      the `md` breakpoint, body scroll locked while open.
- [ ] Recipe count badge reflects the current filtered `total`.
- [ ] Card: image, name, time, serves, category badges (no cap), heart
      (hidden if anonymous, optimistic toggle per decision 4). No cart
      icon, no pending-approval indicator (moved to the detail page,
      decision 5).
- [ ] Grid: 1 col `< sm`, 2 cols `sm`–`lg`, 3 cols `xl+`
      (`ResponsiveRecipeGrid.tsx` breakpoints).
- [ ] Infinite scroll: `IntersectionObserver` sentinel, 200px
      `rootMargin`, 500ms re-trigger debounce, loading skeletons while
      fetching next page, cascade-in animation on both initial load and
      newly-appended cards (decision 8).
- [ ] Changing any filter resets to page 1 and scrolls to top.
- [ ] Empty states: "no results" (filters active — shows active filter
      count + "Clear all filters") vs. "no recipes yet" (unfiltered,
      catalog genuinely empty) — distinct copy, `NoResults.tsx` pattern.
      "Add Recipe" CTA inside these states is disabled (CFE-010 not
      shipped).
- [ ] Filter state fully round-trips through the URL — reload with
      `?categoryId=...&minTime=...` restores the same filtered view.
- [ ] `npm test`, `npm run build`, `npm run lint`, `npm run
      format:check` all clean.
- [ ] Visual + interactive verification below passes.

**Service/API boundary — real requests against real `crockpot-go`, per

## Roadmap

Lower layers first; the `CROC-043`-blocked slider piece goes last so it
doesn't stall everything else.

1. **`AppShell`** — one layout component wrapping every route; auth
   branch lives in `SiteHeader`/`MobileTabBar`, not the shell itself.
   No new data dependency; verify nav + logout by hand, both auth
   states, both breakpoints. **Done** (2026-09-02, commit `06e6fb2`) —
   corrected mid-piece from an initial wrong design (separate
   authenticated-only shell); see decision 1. Founder still owes the
   interactive nav/logout click-through by hand.
2. **`api.ts`** — `listRecipes(params)`, category/item reference-data
   fetchers, favourite mutations. Plain async functions per the Astro
   constraint. **Done** (2026-09-02, commit `ce98114`) —
   `src/features/recipes/{types,api}.ts` + `api.test.ts` (9 tests on
   `buildRecipeListSearchParams`). `getRecipeTimeRange()` deliberately
   **not** built yet — still blocked on `CROC-043`, stays step 6.
3. **`useApiInfiniteQuery` wrapper** — mirrors `useApiQuery`'s
   toast-on-error shape for `useInfiniteQuery`. **Done** (2026-09-04) —
   `src/lib/Tanstack/useApiInfiniteQuery.ts`.
4. **Card + grid** — `RecipeCard` (heart, no cart, no pending indicator
   — decision 5), `ResponsiveRecipeGrid`, infinite scroll + cascade
   animation (add `motion`), empty states. **Done** (2026-09-04) —
   `RecipeCard`/`useToggleFavourite`/`queryKeys` (favourite optimistic
   update, tested), `useRecipeList` (pagination wiring, tested),
   `ResponsiveRecipeGrid`, `RecipeCardSkeleton`, `EmptyRecipes` (tested),
   `RecipeGrid` (orchestrates fetch/scroll/animation/empty-state
   branching), `BrowseRecipesPage`. `motion@^12.43.0` added per decision
   8. Replaces `RecipesComingSoon` at `/recipes` (file deleted). Filter
   params are hardcoded empty (`NO_FILTERS`) and `activeFilterCount` is
   hardcoded `0` until step 5 wires the URL/filter panel — so only the
   unfiltered "No recipes yet" empty state is currently reachable; the
   filtered "No results" branch is built and unit-tested but not yet
   exercised end-to-end.
5. **Search + category/ingredient filters** — URL search-params state,
   `GenericFilterList`-equivalent, active-filter pills, mobile drawer.
   **Done** (2026-09-04) — `useRecipeFilters` (URL round-trip via
   `useSearchParams`, tested), `SearchBar` (300ms debounce, tested),
   `FilterOptionList` (search-within-list + 6-visible/"Show All (N
   more)", tested) reused by `CategoryFilter` (adds the include/exclude
   radio pair) and `IngredientFilter`, `FilterPills` (copy + remove +
   clear-all, tested), `FilterPanel` (composes both filter lists against
   `useReferenceData`'s `useRecipeCategories`/`useItems`, 1hr
   `staleTime` per decision 9), `MobileFilterDrawer` (new
   `components/ui/dialog.tsx` primitive wrapping Radix `Dialog` — gets
   focus trap/Escape/body-scroll-lock for free; adds a
   `matchMedia`-based auto-close past the `md` breakpoint, since Radix
   doesn't do that itself). Wires `BrowseRecipesPage`'s step-4
   placeholders up to real state, adds the recipe-count badge, and
   scrolls to top on filter change (skipped on initial mount) via a
   `previousFilterKey` ref, matching the old app's
   `RecipeGrid.tsx:128-139` pattern. Confirmed against the old app
   (`crockpot/src/app/recipes/`) that categories OR-combine with
   ingredients only in include mode — exclude mode is a separate AND-NOT
   applied by the backend (`CROC-015`), nothing the frontend needs to
   replicate itself, it just sends `categoryId`/`categoryMode`/
   `ingredientId` as independent params.

   **Layout grounded in `browse2.png` over the old app's actual DOM
   shape where they conflict**: the old app keeps `ActiveFilterBadges`
   off mobile entirely and puts a second `SearchBar` instance inside its
   drawer; `browse2.png` instead shows one always-visible row with a
   `[Filters (N)] [pill] [pill]` grouping and the search bar always on
   the page, never inside the drawer — built to match the screenshot,
   per the project's design-grounding rule. The mobile drawer here holds
   only `FilterPanel` (no duplicate search box or clear-all button,
   since both are already reachable on the page).

   **`activeFilterCount` excludes the search query** — time range
   counts as 1, each selected category/ingredient counts individually,
   `q` doesn't add to the count. Diverges from the old app (which counts
   a non-empty query too, `FilterProvider.tsx:79-97`) — deliberate:
   neither screenshot ever shows a "query" pill, and the search box
   already displays its own state, so a query contributing to a
   *removable-pill* count would be misleading. Flagging as a judgment
   call, not a confirmed decision from a grill.

   **Not built**: the time-range slider itself (`setTimeRange` exists on
   `useRecipeFilters` and `FilterPills`/backend already handle
   `minTime`/`maxTime`, but there's no UI control yet) — stays blocked
   on `CROC-043`, sequenced as step 6 below.
6. **`CROC-043`** (separate repo, own grill) → once done, wire the
   time-range slider using its real bounds.
7. `npm test` / `build` / `lint` / `format:check` clean → visual +
   interactive verification → `/code-review medium main` → close-out.
