# CFE-041 — Menu cache consistency

Make every menu mutation update the client's menu cache consistently
with the server: one shared optimistic-mutation hook with per-item revert
and a refetch only after the last failed change, newest-first ordering
to match `GET /menu`, and recipe deletes evicting from the menu.
From tech-debt pass #3, findings 3 and 5
(`docs/findings/2026-09-27-tech-debt.md`). Grilled 2026-09-27. Depth:
expensive to undo, because it sets the pattern later menu mutations
(`CFE-008`, `CFE-012`, `CFE-015`) will copy. AI-driven.

## Facts checked before deciding

- `GET /menu` orders newest first: `ListMenuEntries` has
  `ORDER BY rme.created_at DESC` (`crockpot-go/internal/sqlc/queries/menu.sql`).
  The client's optimistic add appended to the end (`useAddToMenu.ts`,
  `upsertEntry`'s `index ?? entries.length`), so an added recipe jumped
  from the bottom to the top on the next refetch.
- Re-adding (undo) goes through `POST /menu/entries`, which inserts a new
  row with a fresh `created_at`. The server cannot restore a removed
  entry's position.
- Recipe delete (`crockpot-go/internal/repository/recipe.go` `Delete`)
  only runs `DELETE FROM recipes`. Menu entries go via
  `ON DELETE CASCADE` (`db/migrations/000001_init.up.sql:162`); shopping
  lists are **not** resynced. That is a backend gap, filed as
  `crockpot-go` `CROC-058`, and out of scope here.
- Precedents: `useToggleFavourite` reverts only its own change on error
  (`useToggleFavourite.ts:78-91`); `shopping-list/utils/refetchAfterLastChange.ts`
  refetches only when the settling mutation is the last in flight under
  a shared `mutationKey`.

## Decisions

1. **Newest at the top.** An optimistic add inserts at `index ?? 0`, not at
   the end, so the optimistic order matches the server's. Rejected: the
   server switching to oldest-first (a backend change, and newest-first
   suits a menu built up over the week).
2. **Refetch only after a failure, and only when it is the last menu
   change settling.** No refetch after success: the server applies no
   transformation to a menu entry, so each optimistic result already
   equals the server's. Rejected: always refetching like the shopping
   list, which exists because the server does transform list quantities.
   Revisit if the server ever changes a menu entry beyond what was sent
   (e.g. clamping serves); the switch is one line in the shared hook.
   **Refined while building (2026-09-27):** as first worded, a failure that
   settles while another menu change is in flight skipped its refetch,
   and the other change's success never refetches, so the corrective
   refetch was lost. A failure now marks the menu query stale
   (`invalidateQueries` with `refetchType: "none"`), and whichever menu
   change settles last refetches if the menu is stale. Same intent: one
   refetch per failure burst, none after successes.
3. **Undo keeps restoring the original slot**, unchanged from today. The
   helper must preserve add's `index` override, which
   `useUndoableMenuRemoval`'s `undo` passes. Accepted consequence: the
   restored recipe moves to the top on the next natural refetch (a
   return to `/menu` after the 5-minute stale window, or after a failed
   change). Rejected: placing it at the top immediately (a visible jump
   at the moment of undo), and a server-side position-preserving undo (an
   API change for a cosmetic edge; revisit only if the later move bothers
   anyone in practice).
4. **Recipe delete evicts the menu entry from the cache directly and
   invalidates the shopping list.** Eviction matches how `useDeleteRecipe`
   already treats the browse-list caches and needs no request. The
   shopping-list invalidation fetches the (currently stale) server copy
   today, and needs no client change once `CROC-058` lands.
5. **Shape**: a menu-specific `useOptimisticMenuMutation({ mutationFn,
   apply, revert })` in `menu/hooks/`, built on `useApiMutation`. It owns
   the shared `mutationKey` (new `menuKeys.change()`), cancelling menu
   fetches, `apply` on mutate, `revert` plus the guarded refetch on error,
   and shopping-list invalidation on success. The four hooks each keep
   only their request and a pure `apply`/`revert` pair, where each
   `revert` captures only its own before-state:
   - add: if the recipe was already on the menu, restore its serves and
     slot; otherwise remove it;
   - remove: re-insert the entry at its old index if it isn't present;
   - serves: restore the old serves;
   - clear: re-insert the cleared entries that aren't present, below any
     entries present now.

   The refetch guard moves from `shopping-list/utils/refetchAfterLastChange`
   to `lib/tanstack/refetchAfterLastMutation(queryClient, mutationKey,
   queryKey)`, and both features call it. Rejected: a generic
   optimistic-mutation hook in `lib/`, which would abstract from two
   callers that already differ (always-refetch vs error-only).
6. **Accepted worst case**: a Clear overlapping an in-flight add that
   reaches the server after the clear leaves the client empty while the
   server holds the recipe, until the next stale refetch. This is not
   reachable from today's UI: Clear is behind a modal on the Menu tab,
   where the only add is undo, whose tile sits under the modal. The
   reachable overlap (a serves change reaching the server after a clear)
   fails, reverts as a no-op and triggers the corrective refetch. Hence
   the no-op requirement below.

## Acceptance criteria

- [ ] `refetchAfterLastMutation` lives in `lib/tanstack/`; shopping-list
      hooks call it with their own keys and behave exactly as before.
- [ ] All four menu mutations share `menuKeys.change()` as `mutationKey`.
- [ ] Adding a recipe not on the menu puts it at index 0; an explicit
      `index` (undo) is still honoured.
- [ ] A failed menu mutation reverts only its own change; a concurrent
      mutation's optimistic change survives.
- [ ] Every `revert` is a no-op when its target is already absent or
      changed.
- [ ] A failed menu mutation marks the menu stale; the last menu mutation
      to settle refetches `GET /menu` if it is stale; a burst of only
      successes never refetches the menu.
- [ ] Every successful menu mutation invalidates the shopping list (as
      today).
- [ ] Undo after remove restores the recipe to its original slot; a failed
      undo shows the "Removed" tile again with Undo disabled (as today).
- [ ] Deleting a recipe removes it from the cached menu and invalidates
      the shopping list.

## Non-goals

- Server-side shopping-list resync on recipe delete (`CROC-058`).
- Position-preserving undo on the server.
- Detecting or refetching after overlapping *successful* mutations
  (decision 6).
- Multi-tab/multi-device menu sync.
