## Summary

The recipe detail page: hero (image, title, badges, time/serves/by-line,
categories, owner/viewer action row), an optional description, and
ingredients/instructions/notes below — tabbed on mobile, side-by-side on
desktop. Ships a new, more prominent Add-to-Menu hero CTA, decouples
on-page serves display from the menu entirely, adds a mobile-only
collapsing/sticky hero, and a `from`-aware back button. Closes out
Epic 2 — every backend dependency (`CROC-015/016/018/019`) is already
live.

## Decisions and why

### 1. Design screenshots are a style/layout reference, not a literal spec

Founder's framing for this specific ticket: the new screenshots are
"flavour," and several deliberate hybrids of the old app + the new
design follow — recorded as decisions 2–6 below. This is a ticket-scoped
call, not a change to the project's general design-artifact-grounding
rule (`CLAUDE.md`), which still applies everywhere else and to anything
in this ticket not called out as a deviation (hero content/order,
description placement/styling, ingredient-item row layout, categorised
ingredient cards).

### 2. Mobile keeps the old app's Ingredients/Instructions tabs, not the new screenshots' single scroll

The new screenshots (`detail2.png`/`detail3.png`) show one continuous
mobile scroll with no tabs. Founder's explicit call: keep the old app's
tab-based mobile layout (`RecipeContent.tsx`) instead — switching
between the two views needs to be easy, and a long single scroll makes
that worse. Desktop is unaffected either way (side-by-side in both the
old app and the new screenshot, no conflict there). Chef's Notes bundle
into the Instructions tab on mobile (below the steps), matching the old
app — the tab bar only has two tabs, nowhere else for Notes to go.

### 3. New hero Add-to-Menu CTA, not the existing compact icon button

Old app precedent: the exact same compact `AddToMenuButton` (small
circular cart icon, expands inline to a stepper) is reused unchanged on
both the browse card and the detail page — `crockpot-react` already has
this component (`CFE-020`). Founder's call: build a new, larger,
labelled CTA for the detail page instead ("Add to Menu" idle state; "In
Menu" + a serving-count badge once added) — this app's core value
proposition (getting a recipe onto the menu) should read as the primary
action here, not an icon sized the same as edit/delete/favourite.
**Reuses `useAddToMenuButtonState` unchanged** — new presentation only,
no new mutation logic. Animation language is ported directly from the
existing compact button: idle icon+label → tap → icon slides aside,
label fades, a −/qty/+/confirm stepper slides into its place (+
"Remove" if already in the menu), same spring/fade choreography, just
at the larger CTA's scale. Exact corner/edge placement of the in-menu
count badge is a visual-polish detail to settle once it's actually
rendered, not specified further here.

### 4. Serves is fully decoupled from the menu — a real behavior change from the old app

Old app: the ingredients-section serves stepper is disabled entirely for
authenticated users (`useRecipeServes.ts`'s `canAdjustServes:
!isAuthenticated`) — serves comes only from the menu entry if the
recipe is in the menu, otherwise the recipe's default. Only anonymous
visitors got a working local stepper.

New behavior (explicit founder call): **every viewer gets a working
ingredients-section serves stepper (1–50, matching `CFE-020`'s bounds,
not the old app's 1–20)**, logged in or not. It *initializes* from the
menu entry's serves if the recipe is already in the menu, otherwise from
the recipe's own `serves` — but adjusting it is local/view-only and
**never writes to the menu**. The Add-to-Menu CTA (decision 3) owns a
fully separate serving value, used only when adding/updating the actual
menu entry. Example: a recipe defaults to serves 4, is added to the menu
at 8 — the ingredients section initializes showing quantities scaled for
8, but the viewer can then locally flip it to 6 to check quantities
without that touching the menu's stored serving count at all. Rejected:
the old app's locked/menu-derived behavior for authenticated users —
inconsistent UX between anonymous and authenticated users for no benefit
once the two concerns (viewing scaled quantities vs. what's actually on
the menu) are properly separated.

### 5. Mobile-only collapsing/sticky hero — pure CSS `position: sticky`, no scroll-listener/JS state machine

Founder wants (mobile only): a shorter initial hero (less than the
screenshots' ~2/3 viewport height) with title/meta/categories/actions
higher up; scrolling past a point pins the action-button row directly
under the site header with the residual hero image fading into a blur
behind it, the Ingredients/Instructions tab bar pins directly beneath
that in turn, and only the active tab's content scrolls underneath both
— reversing cleanly scrolling back to the top.

Implementation, confirmed against current source rather than assumed:
`SiteHeader` (`SiteHeader.tsx:17`) is already `sticky top-0 z-50`,
`h-16`. The action-button row is the *last* element inside the hero
block, given `sticky top-16` — CSS handles the pin/un-pin transition
natively as its natural position scrolls above/below that offset, no
`IntersectionObserver`, no scroll listener, no `motion` scroll hooks.
The row carries a **permanent** frosted/blurred background band (not a
state-swapped one) so it looks correct both in its natural position
(over the hero image, matching the existing circular buttons'
`bg-white/90 backdrop-blur-sm` treatment) and pinned (over whatever has
scrolled up behind it). The tab bar gets the same `sticky` treatment,
positioned directly below the action row's height, so it naturally
stacks and pins in turn. **Desktop is entirely unaffected** — action row
stays inline in the hero per `detail1.png`, nothing pins.

### 6. Public route, no auth required

`/recipes/:id` matches `/recipes`'s pattern and the backend's
`GET /recipes/:id` (`OptionalAuthMiddleware`, `CROC-015`). Favourite/
edit/delete/Add-to-Menu actions conditionally render on
`isAuthenticated` (+ ownership/admin for edit/delete) — same branching
`RecipeCard.tsx` already uses.

### 7. `from=`-aware back navigation, ported from the old app's `BackButton.tsx`

Deliberately **not** `navigate(-1)`/browser-history-back: that breaks on
a direct URL visit or a shared link with no prior in-app history, which
is exactly the scenario a "back to where you came from" control needs
to handle gracefully. Ported pattern instead: whoever links to the
detail page sets `?from=<path>`; the page falls back to `/recipes` when
it's absent or unrecognized. Desktop shows an adaptive labelled button
("← Back to recipes", matching `detail1.png`); mobile shows a plain
icon-only back arrow (matching `detail2.png`, no label). Only `/recipes`
is a real source today — `RecipeCard.tsx`'s link gains `?from=/recipes`
in this ticket. **`CFE-006`/`007`/`008` register their own `from` values
and back-button labels when they start linking here** — this ticket only
builds the mechanism and its one known caller. Post-delete navigation
(decision 11) reuses the same resolved `from` destination as the back
button — one "return to where you came from" rule, not two.

### 8. Favourite-toggle cache patch extended to the detail query

`useToggleFavourite.ts`'s optimistic update currently only patches
list-query caches (`recipeKeys.lists()`). Extended here to also patch
this recipe's own detail-query cache entry (new `recipeKeys.detail(id)`
key) — otherwise toggling favourite from the detail page would leave the
page's own displayed state stale relative to what it just requested.

### 9. New ingredient-category icon mapper — explicit founder call to keep icons the new screenshots dropped

No icon-name → Lucide-component mapper exists yet anywhere in
`crockpot-react` (the old app's `getIconComponent`/`icon-map.ts` was
never ported, since browse only ever needed recipe-category badges by
name, not `item_categories.icon`). New screenshots show plain text
category headers with no icons; founder wants them back — categories
should be identifiable by more than name alone. Ingredients group by
`itemCategoryName` (from `CROC-015`'s `HydratedIngredient`), same
grouping shape as the old app's `groupIngredientsByCategory`, headers
carry the mapped icon.

### 10. Pending-approval indicator: no screenshot covers this state

The mockup recipe is already approved, so nothing to ground this
against per the usual rule — flagged rather than guessed silently. Built
as a plain highlighted banner above the hero content, own-recipe-only
("Pending approval — visible only to you until an admin approves it"),
read-only (no approve action here — that's `CFE-014`). Backend
visibility (`CROC-015`'s predicate) already guarantees no other viewer
ever sees it, so no extra guard needed beyond "is this my own recipe."

### 11. Edit links to a route that 404s until `CFE-010`; delete is fully functional today

Same precedent as `CFE-004` decision 12 (browse card linking to this
ticket's own not-yet-built route) — `/recipes/:id/edit` 404s into the
catch-all until `CFE-010` ships, acceptable since nothing about this
ticket depends on it. Delete works today (`CROC-016` is live): shadcn
`Dialog` confirm (port the old app's `DeleteRecipeButton.tsx` copy/
pattern) → on success, navigate to the resolved `from` destination
(decision 7) and evict the recipe from any cached list pages (it's gone,
no reason to keep it around stale).

### 12. Recipe-not-found / hidden-recipe state reuses the existing `StatePanel`

No new UI needed — same component `EmptyRecipes.tsx` already uses.
Heading "Recipe not found," a link back to `/recipes`. No distinction
between "doesn't exist" and "exists but hidden from you" (someone else's
unapproved recipe) — matches the backend's own enumeration-defense
collapse, both are a plain 404.

### 13. New `getRecipe`/`deleteRecipe` API functions

Neither exists yet in `src/features/recipes/api.ts`. Added as plain
async functions per the Astro-migration constraint (master spec) —
wrapped by `useApiQuery`/`useApiMutation` in the page component, not
written inline.

## Non-goals

- The actual edit form — `CFE-010`; this ticket only wires the link
  (decision 11).
- Menu-tab / favourites-tab / my-recipes-tab entry points into this page
  — `CFE-006`/`007`/`008` register their own `from=` values when built
  (decision 7), not this ticket.
- Match/ranking badges (`CFE-021`) — browse-only, never shown on detail.
- Writing servings changes back to the menu from the ingredients-section
  stepper — decision 4 makes this explicitly local/view-only.
- Admin approve action beyond the read-only pending banner — `CFE-014`.
- Dark mode — unchanged project-wide non-goal.

## Verification mode

**Anything interactive — hands-on by the founder, the mode that matters
most for this ticket.** `npm run dev` here + `crockpot-go` locally;
project `CLAUDE.md`: Claude doesn't start/poll/drive a dev server to
self-verify visual work. Click through: the mobile collapsing/sticky
hero scroll (pin → blur → tabs stick → content scrolls → reverses
cleanly scrolling back up), the new hero CTA's expand/confirm/remove
animation on both viewport widths, the ingredients-section serves
stepper vs. the CTA's own independent serves value, tab switching,
delete confirm, and the `from`-aware back button from at least one real
entry point (a browse card).

**Anything visual.** No PNG exists for several of this ticket's actual
target states (mobile collapsed/sticky hero, the new hero CTA, the
pending-approval banner, the not-found state) — screenshots are a style
reference only here (decision 1), not something to diff pixel-for-pixel.
Desktop's static layout can be checked directly against `detail1.png`.

**A service or API boundary — real requests against real `crockpot-go`
locally, per piece as it lands.** `getRecipe`: an approved recipe, the
viewer's own unapproved recipe, someone else's unapproved recipe
(expect 404). `deleteRecipe` against a real owned recipe row.

**Logic with assertable behaviour — failing test first (Vitest +
Testing Library), per this project's test policy** (branching/state-
transition logic, not trivial JSX): serves-scaling math, the
ingredient category-grouping helper, the `from=` fallback resolver, the
owner/admin permission check gating edit/delete visibility, the
pending-approval banner's own-recipe-only condition, and the extended
favourite-toggle cache patch (list + detail caches both flip together).

**Limits — exercised through the real client, not just a unit test.**
Confirm the ingredients-section serves stepper's plus/minus buttons
actually disable at 1 and 50 against real rendered state, matching
`CFE-020`'s bounds precedent for the separate menu-serves stepper.
