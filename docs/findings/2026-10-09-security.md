# Security review — 2026-10-09

First whole-codebase security pass (`CFE-064`), done by hand before
go-live, right after `crockpot-go`'s (`CROC-076`,
`../crockpot-go/docs/findings/2026-10-09-security.md`), so the boundary
between them was read from both sides. Scope: `src/` — token handling,
the HTTP client, XSS sinks, redirects built from query params, the reset
and OAuth callback pages, browser storage, cache clearing between users,
`VITE_` exposure, dependencies. Security headers aren't checked here:
they're `CFE-044`, blocked on the first Vercel deploy.

3 findings: one low and confirmed (an open redirect), one low
(dependency advisories, none shipped to the browser), one informational.
The biggest remaining gap is the open `CFE-044` (no CSP or other headers
yet).

## Findings

### 1. Open redirect from `?from=` on a modified click — low, confirmed

**File**: `src/features/recipes-detail/hooks/useRecipeBackDestination.ts`
(`isSafeRelativePath`)

The check `/^\/[^/\\]/` only rejects `/` or `\` as the second character.
`?from=/%09/evil.com` decodes to `/\t/evil.com`, passes, and is rendered
verbatim into the back link's `href`. The URL parser strips tabs and
newlines, so the `href` resolves to `//evil.com`. Confirmed with a
throwaway test rendering the real `<Link>` and resolving its `href` with
WHATWG `URL`: `host` is `evil.com` for both `\t` and `\n` (a literal
`%09` stays on-site). A plain click is safe, because React Router
navigates in-app; a middle-click, cmd/ctrl-click or "open in new tab"
follows the raw `href` off-site from a link that looks like
`crockpot.app`. This answers the open question `CFE-052` left.

**Fix**: accept only paths in `BACK_LABELS` plus `/recipes…`, or reject
any control character or whitespace before applying the regex. Add the
`\t`/`\n` cases to the hook's tests.

### 2. Two high-severity `npm audit` advisories, both build- or test-time — low

`npm audit`: `source-map-js` 1.2.1 (via `vite`/`@tailwindcss/vite`,
GHSA-68fv-2mgg-jv7q) and `undici` 7.29.0 (via `jsdom`, ten advisories).
Neither is in the bundle sent to the browser: one runs during the build,
the other during tests. Real exposure is near zero, but a clean audit
keeps real advisories visible.

**Fix**: `npm audit fix`, then the test suite and a build.
(`@tailwindcss/vite` sits in `dependencies` though it's build tooling;
that's not a security issue, just why the prod-only audit lists it.)

### 3. Ids from the URL go into API paths unencoded — informational

**Files**: `src/features/recipes/data/api.ts` and the other `data/api.ts`
wrappers; `RecipeDetailPage.tsx`, `EditRecipePage.tsx` (`useParams`)

React Router decodes route params, so `/recipes/x%2F..%2F..%2Fmenu` gives
`id = "x/../../menu"`, and `apiFetch(`/recipes/${id}`)` sends an
authenticated request to `/menu` after the URL parser collapses the dot
segments. Not exploitable today: the URL-derived id only feeds the read
(`useRecipe(recipeId)`), and every write uses `recipe.id` from the API
response (`EditRecipePage.tsx:16`, `RecipePendingApprovalBanner.tsx:16`).
A future page that fires a write from a route param would turn this into
a cross-site request forgery.

**Fix (defence in depth)**: `encodeURIComponent` ids in the API
wrappers, or redirect when a route param isn't a UUID.

## Checked clean

- **Access token** lives only in memory (`src/lib/http/tokenStore.ts`);
  only the `HttpOnly` refresh cookie persists. One refresh in flight at a
  time; a 401 on refresh ends the session through one path.
- **No XSS sinks**: no `dangerouslySetInnerHTML`, `innerHTML`, `eval` or
  `new Function` anywhere in `src/`. Dynamic `href`s are only
  `mailto:${CONTACT_EMAIL}` (a constant); `<img src>` values come from
  API data and can't execute script.
- **OAuth callback** shows `?error=` only through a fixed message map
  with a generic fallback (`auth/data/types.ts` `getAuthErrorMessage`),
  so arbitrary text can't be injected. No token or user data travels in
  the redirect.
- **Reset token** is read from `?token=` and only ever sent to the API in
  a POST body. It stays in the address bar and history until the page
  changes; `CFE-044`'s `Referrer-Policy` keeps it out of `Referer` on the
  page's Google Fonts requests (browsers' default policy already sends
  only the origin).
- **Cache between users**: `endSession` clears the access token and every
  non-session query on logout, account deletion and expired sessions;
  `startSession` does the same on sign-in.
- **Storage**: only a non-sensitive browse shuffle seed in
  `sessionStorage`. **Env**: the only `VITE_` variable is `VITE_API_URL`.
- **Cross-repo**: the client sends `credentials: "include"` to one API
  origin, and the spec's same-site domain layout supports a `Lax`
  refresh cookie. The backend still sets `None`; that's `crockpot-go`'s
  finding 1.
