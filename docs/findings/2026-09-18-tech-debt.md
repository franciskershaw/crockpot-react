### 3. `MIN_SERVES`/`MAX_SERVES` clamp logic duplicated verbatim across two tickets' hooks

**Files**: `src/features/recipes/hooks/useAddToMenuButtonState.ts:9-10,82,95-96`
(`CFE-020`) and `src/features/recipes/hooks/useIngredientServes.ts:6-7,48,55-56`
(`CFE-005`) — both independently declare `MIN_SERVES = 1` /
`MAX_SERVES = 50`, both clamp with the identical
`Math.max(MIN_SERVES, Math.min(MAX_SERVES, amount + delta))`, and both
derive `canDecrease`/`canIncrease` the same way. Both also independently
reset local override state from an upstream value inside a `useEffect`
(`useAddToMenuButtonState.ts:28-32`, `useIngredientServes.ts:40-42`), and
`oxlint` flags both separately with the same `set-state-in-effect`
warning.

**Why it matters**: two different tickets building "adjust a serves
count with 1–50 bounds" independently, never reconciled — the
"duplicated logic added by different tickets" class this audit looks
for. A future bounds change (matching a backend validation change) has
to be made in two places with no compiler link between them.

**Fix**: extract a shared `useBoundedServes`/`clampServes(amount, delta)`
helper both call into; also resolves both `set-state-in-effect` lint
warnings in one place instead of two.

**Ticket**: `CFE-029`.

### 4. A new non-interactive `onClick` div on the stepper controls trips the a11y lint ruleset

**File**: `src/features/recipes/components/add-to-menu/AddToMenuStepperControls.tsx:39-42`
— the serving-count display `<div onClick={stopEvent}>...</div>`
(present purely to stop the click bubbling to the parent `RecipeCard`
`<Link>`, not to be interactive itself).

`npm run lint` flags this exact element with two warnings —
`jsx-a11y(click-events-have-key-events)` and
`jsx-a11y(no-static-element-interactions)`. Pass #1 explicitly checked
and confirmed "nothing custom here fights the oxlint a11y ruleset" —
no longer true; this is a new element, added by `CFE-020`, that does.
(The real stepper buttons and confirm button all correctly use `<button>`s
with `aria-label`s and are clean.)

**Why it matters**: low real-world impact, but it's exactly the pattern
the project's own linter is configured to catch, and it's currently
silently accumulating — `npm run lint` exits `0` despite 16 total
warnings (this one plus 15 others, mostly pre-existing
`react-hooks/exhaustive-deps` and `set-state-in-effect` warnings not new
to this pass), so nothing currently surfaces this in CI or pre-commit
(`lint-staged` only runs `oxlint --fix`, which doesn't auto-fix semantic
warnings like this one).

**Fix**: swap the `<div onClick>` for a `<button type="button" tabIndex={-1}>`
styled to look identical, or move the stop-propagation up to the
stepper's own outer wrapper (which already has no click handler of its
own) rather than on the text display itself.

**Ticket**: `CFE-028`.

**Why it matters**: `RecipeFavouriteButton` predates `CFE-005`;

**Fix**: a small shared `RecipeHeroIconButton` wrapper (or an exported
`RECIPE_HERO_ICON_BUTTON_CLASSES` constant, mirroring `RecipeHero.tsx`'s
own `ACTION_BUTTON_CLASSES` pattern one layer up) that all three compose

**Ticket**: `CFE-029`.

### 6. Dangling `setTimeout` in `FilterOptionList`'s expand handler, never cancelled

**File**: `src/features/recipes/components/FilterOptionList.tsx:65-75`
(`handleToggleShowAll`) — fires a bare
`setTimeout(() => sectionRef.current?.scrollIntoView(...), EXPAND_SCROLL_DELAY_MS)`
on expand, with no `clearTimeout` and nothing tracking the timer's id.

**Why it matters**: not inside a `useEffect` so it doesn't fit pass #1's
cleanup checklist directly, but it's the same class of bug — toggling
"Show more"/"Show less" twice within the 100ms window still fires the
stale timeout and scrolls the (now-collapsed) section into view.
Optional-chaining on `sectionRef.current` means it won't throw
post-unmount, so this is a UX correctness gap, not a crash risk.

**Fix**: track the timeout id in a `useRef` and `clearTimeout` it at the
start of `handleToggleShowAll` before scheduling a new one.

**Ticket**: `CFE-030`.

**Why it matters**: the one line that fixed a real, previously-shipped

**Fix**: add one `useMenuEntry.test.tsx` case — `getMenu` rejecting, no
cached data — asserting `isPending: true`, mirroring the existing "no
cached data yet" case's shape.

**Ticket**: `CFE-027`.
