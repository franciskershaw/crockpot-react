### 1. The main bundle now carries `motion`, `zod`, `react-hook-form`, `cmdk` and Radix Select for every visitor *(reopened)*

**Files**: `src/app/AppRoutes.tsx:6-9,14` (eager imports of
`MenuPage` and the three `your-crockpot` pages, and the comment
justifying it); heavy importers reached from there:
`features/menu/pages/MenuPage.tsx`, `menu/components/AnimatedMenuSlots.tsx`,
`shopping-list/components/{QuantityControl,ShoppingListCategory}.tsx`
(`motion`), `CreateItemDialog.tsx` (`zod` + `react-hook-form` +
`@hookform/resolvers`), `AddItemSearch.tsx`/`UnitMultiSelect.tsx`
(`cmdk`), `AddItemEditor.tsx`/`CreateItemDialog.tsx` (Radix Select).

`npm run build` now emits Vite's "chunks larger than 500 kB" warning:
`index-*.js` is 742 kB (235 kB gzip). Pass #2 recorded no warning. A
source-map breakdown of the main chunk has `motion-dom` + `framer-motion`
(~457 kB of source), `zod` (~359 kB) and `react-hook-form` (~135 kB) as
the biggest non-React contributors. None of them were in the eager bundle
at pass #2.

`CFE-019` lazy-loaded only the routes carrying `motion`, on purpose, and
left `MenuPage` eager because it was "most visitors' first view and gain[s]
nothing from a chunk round trip" (the `AppRoutes.tsx:14` comment).
Pass #2 re-checked this and confirmed `motion/react` stayed out of the
eager landing/menu bundle. `CFE-006` reversed that without revisiting the
decision. The landing page, the only page anonymous visitors see, now
downloads the whole menu + shopping-list + admin create-item stack.

**Why it matters**: the premise behind the eager-`MenuPage` choice no
longer holds, and the cost lands on the landing page. That is the one
route where first-load weight matters most, and the one that never uses
any of this code.

**Fix**: lazy-load `YourCrockpotLayout` and its three child pages with
the existing `lazyNamed` helper (landing stays eager). Consider lazily
splitting `CreateItemDialog` too, since it is admin-only. Update the
`AppRoutes.tsx` comment either way. Verify with `npm run build`: the
warning is gone and `index-*.js` has no `motion`/`zod`.

**Ticket**: `CFE-039`.

### 2. Menu tab and shopping list render blank while loading and after a failed load *(reopened class, new sites)*

**Files**: `src/features/menu/pages/MenuPage.tsx:51-52,91` (`entries && (…)`:
nothing renders until data exists, and nothing ever renders if `GET /menu`
fails); `src/features/shopping-list/components/ShoppingListPanel.tsx:29,63`
(`grouped && (…)`: same for `GET /shopping-list`; the header, add-extra
row and footer render around an empty body, so the footer reads "Built
from 0 recipes on your menu" whether the menu is empty or failed to load).
`useMenu`/`useShoppingList` go through `useApiQuery`, so a failure raises
one transient toast and then leaves the blank.

This is the exact class pass #1 filed as finding 2 for the browse grid
(`CFE-016`: "relying on a transient toast that left the browse grid
silently blank after it faded"). `RecipeGrid` and `RecipeDetailPage` now
both have real pending and error states built on `StatePanel`. The two
new `CFE-006` surfaces don't use them.

**Why it matters**: the Menu tab is the default authenticated route
(`DEFAULT_AUTHENTICATED_ROUTE`), so it is the first screen after sign-in.
A slow or failed `GET /menu` gives a header with nothing under it and no
retry. `YourCrockpotLayout`'s subtitle falls back to plain "Your
Crockpot" at the same moment, which hides the failure further.

**Fix**: give both surfaces a pending state and an error state with
retry, following `RecipeGrid`/`RecipeDetailPage`. The pending state
should use `CFE-038`'s shared delayed-fade skeleton wrapper, whose own
backlog note says to extract it "when `CFE-006` … adds its first
skeleton". This is that point, so do the extraction here and not as a
separate ticket.

**Ticket**: `CFE-040`.

### 3. Deleting a recipe leaves it in the cached menu

**Files**: `src/features/recipes/hooks/useDeleteRecipe.ts:28-33`, whose
`onSuccess` evicts the recipe from `recipeKeys.lists()` and removes
`recipeKeys.detail(id)`, but doesn't touch `menuKeys.menu()` or
`shoppingListKeys.list()`.

Server side, `crockpot-go`'s `recipe_menu_entries.recipe_id` is
`ON DELETE CASCADE` (`db/migrations/000001_init.up.sql:162`), so deleting
a recipe silently takes it off the owner's menu. The client's menu cache
keeps it for up to the default 5-minute `staleTime`, with
`refetchOnWindowFocus: false` (`lib/tanstack/queryClient.ts`). Repro: add
your own recipe to the menu, delete it from its detail page, open the
Menu tab. The deleted recipe is still there, and clicking it lands on a
404.

**Why it matters**: reachable today from the detail page's delete button
(`CFE-005`), and it gets much more likely once `CFE-008` puts edit/delete
on the My recipes tab, next to the menu in the same layout.
`useToggleFavourite` already shows the precedent: it reaches into the
menu cache (`useToggleFavourite.ts:67,75`) to keep a cross-feature copy
of the recipe consistent.

**Fix**: in `useDeleteRecipe`'s `onSuccess`, drop the entry from the
menu cache, or invalidate `menuKeys.menu()`, and invalidate
`shoppingListKeys.list()` too. Whatever the server does to the list on
a recipe delete (not checked this pass), the client copy shouldn't be
trusted afterwards. Add a test case asserting both.

**Ticket**: `CFE-041`.

### 4. No security headers on the deployed SPA *(time-coupled to the first Vercel deploy)*

**File**: `vercel.json`, which holds only the SPA rewrite. No
`Content-Security-Policy`, `X-Content-Type-Options`, `Referrer-Policy`, or
`frame-ancestors`/`X-Frame-Options`.

Not raised by either earlier pass (the findings docs have no mention of
headers or CSP). The auth design (master spec, "Key architecture
decisions") keeps the access token in memory specifically to avoid XSS
token theft. That only limits what an XSS can steal. It doesn't stop the
XSS from making authenticated calls itself, and a CSP is the layer that
makes XSS harder to land in the first place. Clickjacking protection
(`frame-ancestors`) is also relevant for an app with one-click
destructive actions (clear menu, delete recipe).

**Why it matters**: cheap to add, awkward to retrofit once more
third-party origins are in play. The allowlist needs Google Fonts now,
the API origin (`VITE_API_URL`), and Cloudinary's upload widget once
`CFE-010` lands.

**Fix**: add a `headers` block to `vercel.json`. Start the CSP in
`Content-Security-Policy-Report-Only` against a preview deploy, then
enforce. **Blocked on the first Vercel deploy** (`CFE-001`: "Vercel
deferred until `crockpot-go` deploys"). Revisit the allowlist at
`CFE-010` for Cloudinary.

**Ticket**: `CFE-044`.

## Low severity

### 5. The four menu mutation hooks copy the same optimistic boilerplate, including a whole-snapshot rollback that can drop a concurrent change

**Files**: `src/features/menu/hooks/useAddToMenu.ts:42-55`,
`useRemoveFromMenu.ts:30-43`, `useUpdateMenuEntryServes.ts:37-50`,
`useClearMenu.ts:18-29`. Each repeats the same steps: `cancelQueries`,
snapshot `previous`, `setQueryData`, then `onError` restores `previous`
and invalidates the menu, and `onSuccess` invalidates the shopping list.
They differ only in the cache transform (about 5 lines each).

The duplication has a correctness edge. On error, each hook restores a
**whole-menu snapshot** taken at its own `onMutate`, which erases any
other menu mutation's optimistic change made since. Then it invalidates
the menu without the `isMutating` guard. For example, a failing
remove-A overlaps an add-B from a browse card: A's rollback wipes B's
optimistic entry, and the unguarded refetch can land before B commits.
B's `onSuccess` doesn't refetch the menu, so B shows as not on the menu
until the next stale refetch. `CFE-006` already solved this for
`shopping-list/` (`mutationKey: shoppingListKeys.change()` +
`refetchAfterLastChange` guarded by `isMutating`, per LESSONS
2026-09-27), and `useToggleFavourite` solved it with a per-item revert
(`useToggleFavourite.ts:78-91`). The menu hooks follow neither.

**Why it matters**: needs a server failure to trigger, hence low. But
the same fix has to be applied four times by hand, and the sibling
feature already has the right pattern.

**Fix**: give the menu hooks a shared `mutationKey` and an
`isMutating`-guarded refetch on settle, mirroring
`refetchAfterLastChange`, through one small shared helper (e.g.
`optimisticMenuUpdate(queryClient, transform)`) that all four call with
their transform.

**Ticket**: `CFE-041`.

### 6. The two quantity editors validate input differently

**Files**: `src/features/shopping-list/components/AddItemEditor.tsx:15,66,109`
(input restricted by `QUANTITY_PATTERN = /^\d{0,4}(\.\d{0,2})?$/`, so at
most 9999.99 with 2 decimal places, filtered as the user types) vs
`src/features/shopping-list/components/QuantityControl.tsx:27,136`
(free text; valid if `Number(draft)` is finite and > 0, so `"1e5"`,
`"0x10"` and `"123456789"` all pass). The same `focusAtEnd` ref callback
is also copied in both files (`AddItemEditor.tsx:69`,
`QuantityControl.tsx:29`) and again as an effect in
`CreateItemDialog.tsx:78`.

**Why it matters**: the same field (a shopping-list quantity) accepts
different values depending on whether the item is being added or edited.
The editing path accepts inputs the adding path deliberately blocks.

**Fix**: share one quantity parse/validate helper (in
`shopping-list/utils/`) and one `focusAtEnd` ref callback, both used by
both editors.

**Ticket**: `CFE-042`.
