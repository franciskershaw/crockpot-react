## Summary

A per-card cart icon on `RecipeCard`, ported behaviourally unchanged from
the old Next.js app's `AddToMenuButton.tsx` (cart icon → expands to a
serving-count stepper with confirm/cancel/remove — Framer Motion spring
transitions throughout), now buildable because `CROC-019` shipped
`GET /menu` / `POST /menu/entries` / `PATCH|DELETE /menu/entries/:recipeId`
(2026-09-06). Same icon, same position, same behaviour on every viewport
— the old app never branched this on breakpoint and neither does this.

## Decisions and why

### 1. Design screenshots are not the reference for this feature — the old app is

`browse1.png` (desktop) shows a per-card cart icon; `browse2.png`
(mobile) shows none, only an unrelated floating global cart FAB with a
count badge. Founder's call (2026-09-07): the mockups are flavour only
for this specific feature: the old app's `AddToMenuButton.tsx` is the
actual reference, ported as close to unchanged as this codebase's stack
allows (same `motion/react` transitions, same expand/collapse/badge
choreography). This is a deliberate, ticket-scoped override of this
project's design-artifact-grounding rule (`CLAUDE.md`) — that rule stays
the default for every other ticket; here it's explicitly superseded by a
better-fidelity reference (a running implementation, not a static mock).

One concrete consequence: no breakpoint branching on the icon itself —
`RecipeCardActions` in the old app has none (`showActions` only branches
on auth), so this port doesn't invent one either, even though
`browse2.png` implies mobile should look different.

### 2. `isInMenu`/`serves` derived client-side from `GET /menu`, not a new card DTO field

`crockpot-go`'s `RecipeCard` DTO carries `IsFavourite bool`
(`internal/models/recipe.go:48`) — CFE-004 decision 4 relies on that,
flipping it in the recipe-list's own query cache, specifically to avoid
cross-referencing a separately-fetched list (the old app's actual
favourites pattern, rejected there). `RecipeCard` has **no** `IsInMenu`
field, and `CROC-019` was never asked to add one.

This ticket does not request one. Instead: fetch `GET /menu` once
(`useQuery`, not paginated — `internal/models/menu.go:5-13` shows a
single hydrated `{entries: [{recipeId, serves, recipe}]}` list), and
derive `isInMenu`/`serves` per card by matching `recipe.id` against it —
the same lookup the old app's `AddToMenuButton.tsx:18-22` does
(`menu?.entries?.find(...)`). This looks like the exact pattern CFE-004
decision 4 rejected for favourites, but the reason doesn't transfer: a
menu is a bounded weekly plan (single-digit-to-teens entries), not an
arbitrarily large list — cheap to hold whole client-side, unlike
favourites.

### 3. `GET /menu` prefetched at `AppShell`, to avoid a flash on first paint

Browse and the future favourites list (`CFE-007`) both render cards from
their own list query, independent of `GET /menu` — so on first paint,
`RecipeGrid` can resolve before the menu query does, and any card that
*is* in the menu would paint "not in menu" and then flip, visibly. (The
heart never has this problem — `isFavourite` arrives atomically in the
same response as the card. The menu tab, `CFE-006`, doesn't either — its
own primary query *is* `GET /menu`, so every card shown there is
trivially already "in menu".)

Fix, two parts:
- `GET /menu` is fetched at `AppShell` mount (`src/components/nav/AppShell.tsx`),
  gated on `useAuth().isAuthenticated` — same root-level-query pattern
  `AuthContext` already uses for the session (`AuthContext.tsx:32-38`),
  giving it a head start over Browse's own (filter-param-dependent,
  reference-data-joined) recipe list query. **Does not** reuse
  `AuthContext`'s `staleTime: Infinity` — a menu is actively mutated
  during the session, so it keeps the project's normal default staleTime
  and stays fresh via optimistic mutation flips (decision 4), not via
  refetch.
- While that query `isPending`, the cart icon renders a neutral/pending
  state — never a false "not in menu" default — and swaps to the derived
  true state once resolved. Only matters on first paint; every later
  infinite-scroll page reads the already-resolved cache, so pagination
  never re-flashes.

### 4. Optimistic mutations flip the `menu` query's own cache, not the recipe list's

`useToggleFavourite` (`features/recipes/hooks/useToggleFavourite.ts`)
optimistically flips the recipe list's own `InfiniteData` cache, because
that's where `isFavourite` lives. Menu state doesn't live there (decision
2) — it lives in the `menu` query's cache, so
`useAddToMenu`/`useUpdateMenuEntryServes`/`useRemoveFromMenu` flip
*that* cache instead (add/update/remove the matching entry), with
rollback in `onError`, same shape otherwise. `RecipeCard` re-derives
`isInMenu`/`serves` from the (now-updated) `menu` cache on every render —
no separate local optimistic state needed on the card itself.

### 5. Menu data layer lives in `features/menu/`, imported into `features/recipes/components/RecipeCard.tsx`

Mirrors `crockpot-go`'s own architectural call that `/menu` is a
top-level resource with its own handler/repository, not a recipe
sub-route (`CROC-019` handoff, "Data layer shape"). `features/menu/`
already exists (`MenuScreen.tsx` stub, untouched by this ticket) — this
ticket adds its `api.ts`/`types.ts`/`queryKeys.ts` plus
`hooks/useMenu.ts` (the query) and `hooks/useAddToMenu.ts` /
`useUpdateMenuEntryServes.ts` / `useRemoveFromMenu.ts` (the mutations),
per the feature-folder rule. Import direction is one-way: `recipes` →
`menu`, never the reverse. Built so `CFE-005`/`CFE-006`/`CFE-007` can
import these hooks directly later — none of this ticket's menu logic
lives buried inside `RecipeCard.tsx` itself.

### 6. Cart icon hidden entirely for anonymous visitors

Same gate the favourite heart already uses
(`RecipeCard.tsx:43`, `isAuthenticated`) — `POST /menu/entries` etc. are
full-auth (`CROC-019` decision 3, no anonymous case at all), and this
matches the old app's own combined gate
(`RecipeCard.tsx:137-138`: `showActions = status === "authenticated"`,
which hid both heart and cart together). Not a new decision, just
extending the existing one to the new element.

### 7. No `AppShell`/nav badge in this ticket

The master-spec's original ticket line ("plus whatever `AppShell` badge
it animates toward") was written off `browse2.png`'s floating cart FAB —
discounted per decision 1. Founder's call (2026-09-07): that FAB was
speculative (a "quicker route to the shopping list than Your Crockpot"
idea), not a feature to build now, and the old app's nav
(`Navbar.tsx`/`BottomMobileNav.tsx`) has never had a cart/menu badge of
any kind. This ticket ships only the per-card green serving-count badge
that's already part of the ported component
(`AddToMenuButton.tsx:137-149`) — nothing in `AppShell`. A global
menu/shopping-list quick-access affordance is parked, not sequenced into
any ticket yet.

### 8. Serves stepper bounds: 1–50, not the old app's 1–20

The old app's stepper hard-caps client-side at 20
(`AddToMenuButton.tsx:86`: `Math.min(20, servingAmount + delta)`).
`crockpot-go`'s actual validation for menu entries is 1–50
(`internal/handler/menu_requests.go:23`, matching a recipe's own
`serves` field per `CROC-019` decision 4). Founder's call: match the real
backend limit, not the old app's arbitrary lower one.

## Deltas from the plan (shipped)

- Close-out code review (2026-09-08, run externally via Cursor's Bugbot +
  security pass, not this project's `/code-review`) found two real
  issues, both fixed:
  - `useMenuEntry`'s pending-state gate, covered above.
  - `useLogout` only reset the auth-session query key on logout, leaving
    every other cached query (`menu`, and by the same gap, favourites)
    to survive a same-tab login as a different user until its next
    refetch — a stale-cache cross-user bleed, not scoped to this
    ticket's own new code but surfaced by it. Fixed by having
    `queryClient.clear()` run before the auth-session key is reset in
    `useLogout.tsx`, so every cached query gets scoped to session
    boundaries going forward, not just `menu`.

## Acceptance criteria

- [x] `RecipeCard` renders a cart icon, top-left (mirrors the heart's
      existing top-right), on every viewport — no breakpoint branching.
- [x] Icon hidden entirely when `!isAuthenticated` (decision 6).
- [x] Click expands cart icon → X/cancel + serving-count stepper (minus/
      plus, 1–50 bounds per decision 8, disabled at bounds) + confirm
      (check) + remove-from-menu (when already in menu) — same
      `motion/react` transitions/timings as
      `crockpot/src/app/recipes/components/AddToMenuButton.tsx`.
- [x] Confirm calls `POST /menu/entries` (upsert); remove calls
      `DELETE /menu/entries/:recipeId`; editing an existing entry's
      serves and confirming calls `PATCH /menu/entries/:recipeId`.
- [x] Green serving-count badge pops in (spring) on the icon when the
      card's recipe is in the menu, matching
      `AddToMenuButton.tsx:137-149`.
- [x] `isInMenu`/`serves` per card derived by matching `recipe.id`
      against the `menu` query's cache (decision 2) — no new backend
      field requested.
- [x] `GET /menu` prefetched at `AppShell` mount, gated on
      `isAuthenticated` (decision 3).
- [x] Cart icon shows a neutral/pending state (not "not in menu") while
      the `menu` query is still pending on first paint, **and while it
      has errored** — the pending/error distinction wasn't in the
      original plan; a code-review pass at close-out (2026-09-08) found
      `useMenuEntry` only checked `isPending`, so a failed `GET /menu`
      still rendered as a plain, clickable "not in menu" icon. Folded
      `isError` into the same neutral-state flag (decision 3).
- [x] Add/remove/update-serves mutations optimistically flip the `menu`
      query cache with `onError` rollback (decision 4); `RecipeCard`
      re-derives from that cache, no separate local optimistic state.
- [x] Menu data layer lives in `features/menu/`, imported one-way into
      `features/recipes/components/RecipeCard.tsx` (decision 5).
- [x] `npm test`, `npm run build`, `npm run lint`, `npm run
      format:check` all clean.
- [x] Visual + interactive verification below passes.

## Verification mode

**Visual — side-by-side against the running old app, run by the
founder, not a screenshot comparison.** `npm run dev` here + `npm run
dev` in `../../crockpot` (+ local `crockpot-go`); project `CLAUDE.md`:
Claude doesn't start/drive a dev server to self-verify. This is a
deliberate, ticket-scoped substitution for the usual design-screenshot
check (decision 1) — compare the ported icon's expand/collapse/badge
animation directly against `AddToMenuButton.tsx` running live, not
against `browse1.png`/`browse2.png`.

**Interactive — hands-on by the founder.** Add a recipe to the menu from
a card, adjust serves up/down, confirm, cancel mid-edit without
confirming, remove from menu, repeat starting from a card already in the
menu on page load (exercises the `menu`-prefetch/derivation path, not
just the mutation path) — on both mobile and desktop viewport widths.

**Service boundary — real requests against real `crockpot-go` locally,
per piece as it lands, not batched.** `GET /menu`, `POST /menu/entries`,
`PATCH /menu/entries/:recipeId`, `DELETE /menu/entries/:recipeId` all
already have backend coverage in `crockpot-go/requests/menu.http`
(`CROC-019`); this ticket exercises the same four endpoints through the
real running frontend, not mocked.

**Logic with assertable behaviour — failing test first (Vitest +
Testing Library).** Per this project's test policy (branching/state-
transition logic, not trivial JSX): the menu-entry-derivation helper
(recipeId + `menu` entries → `isInMenu`/`serves`), and the optimistic
mutate/rollback flip against the `menu` query cache (mirrors
`useToggleFavourite.test.ts`'s shape).

**Limits — exercised through the real running client, not just a unit
test.** Confirm the stepper's plus/minus buttons actually disable at 1
and 50 against the real backend validation (decision 8), not just an
asserted constant.
