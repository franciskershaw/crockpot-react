## Medium severity

### 1. A revoked or expired session leaves the app logged in, failing every request

**Files**: `src/lib/http/client.ts:29-41,68-71` (`performRefresh` clears
the access token and throws on a failed refresh; `apiFetch` lets that
error propagate); `src/features/auth/components/AuthContext.tsx:33-38`
(the session query has `staleTime: Infinity` and nothing writes it after
boot); `src/features/auth/hooks/useLogout.tsx:17-24` (the only code that
sets the session to `null` and wipes user caches).

`crockpot-go` answers a refresh with a revoked, reused or expired token
with 401 `invalid_refresh_token` (`internal/handler/auth_handler.go:717-719`;
reuse detection revokes the whole family at `:776-785`). On the client,
any request whose access token has expired then goes 401 → refresh → 401,
and `apiFetch` throws `ApiError(401, "failed to refresh session")`. That
error goes no further than the calling hook's toast. The session query
still holds the user, so `isAuthenticated` stays true. The header still
shows the avatar, `RequireAuth` still lets the user in, and every query
and mutation fails with the same "failed to refresh session" toast. The
only ways out are Log out (which itself fails server-side but clears
locally) or a reload.

Not previously considered: pass #1 (`CFE-017`) tested that the refresh
failure *throws*, and pass #2 checked only that logout revokes server-side.
Neither followed what the UI does once the session dies mid-use.

**Why it matters**: this is how every session ends that isn't a manual
logout: refresh-token expiry, a reuse-detection revoke, or a logout on
another device if the server ever revokes across devices. The worst case
is the recipe form (`CFE-010`). A user who has spent minutes on a recipe
presses Publish, gets a toast that doesn't say what's wrong, and the only
fix (reload) drops the form, behind a "Leave without saving?" prompt that
can't save it either.

**Fix**: when a refresh fails after boot, end the session the way logout
does. Write the session query to `null` and remove the other caches (pull
`useLogout`'s `onSettled` body into a shared `endSession(queryClient)`),
and show one clear toast ("Your session has ended — sign in again") in
place of N generic ones. `client.ts` has no `queryClient` access, so it
needs a small hook-in, for example an `onSessionExpired` callback that
`AuthProvider` registers. `RequireAuth` then redirects on its own. Decide
at the grill whether the recipe form gets anything better than losing its
contents (this overlaps `CFE-048` drafts' open question). Test the case of
several concurrent requests failing together: one toast, one cache wipe.

**Ticket**: `CFE-050`.

### 3. The two undoable-removal hooks are the same hook twice

**Files**: `features/menu/hooks/useUndoableMenuRemoval.ts` and
`features/your-crockpot/hooks/useUndoableFavouriteRemoval.ts`. Both
destructure `useUndoQueue`, both define `remove` as `start` →
`mutateAsync` → `settle`/`forget` (with the same `mutateAsync` comment), and
both define `undo` as `claimUndo` → `mutate`. They differ only in which
mutation removes and which one restores.

**Why it matters**: the `mutateAsync` subtlety (per-call `mutate`
callbacks fire only for the latest call) is the kind of fix that gets made
in one copy and not the other. A third list with undo (Planner, `CFE-012`)
would make a third copy.

**Fix**: a `useUndoableRemoval({ keyOf, remove, restore })` next to
`useUndoQueue` in `lib/`, with the two feature hooks reduced to calling it.
This is **not** the "generic `lib/` hook" `CFE-041` rejected: that was about
the optimistic *menu mutations*. This is the undo bookkeeping above them,
which is already generic in `useUndoQueue`.

**Ticket**: `CFE-051`.

### 7. Recipe limits are hand-written in several places

`recipes-form/utils/recipeFormSchema.ts:69-70` and

## Findings not filed as tickets

  `ReadTimeout` is a flat 10s (`lifecycle.go:39`), with no per-route
  override (no `SetReadDeadline`/`ResponseController` anywhere). The
  deadline covers reading the whole request body, so it includes
  `CFE-049`'s multipart photo. A shrunk photo (≤1600px JPEG at 0.85,
